# Rule Engine · Sentinel 설계: 특이사항 위험 신호와 수치 위험

> 상태(2026-10-27): 구현 순서 1~3번 완료(API 없음). 구현 메모는 문서 끝 "구현 메모" 참고. 4번(재채점)과 5번(R-set)은 아직 하지 않았다.

목적: test 최종 보고(2026-10-26)에서 모든 구성이 놓친 안전 공백을 코드 규칙으로 메운다. 위험 recall이 8구성 모두 2/3이었고 놓친 것은 gs-059(R2)의 "발 부종, 사흘째 식사 거부"다. 값은 특이사항에 기록되지만 flag가 risk가 되지 않는다. 이 설계는 **API를 쓰지 않고** 먼저 규칙으로 해결하는 범위를 정하고, LLM 보조는 그 뒤 선택 단계로 둔다.

## 1. 공백의 정체 (dev·test 현황)
**위험 flag 정답과 현재 Flagger의 포착**

| 분할 | 위험 정답 필드 | 현재 Flagger가 못 잡는 것 | 원인 |
|---|---|---|---|
| dev 30건 | 13개(복약 5, 낙상 3, 혈압 2, **특이사항 3**) | 5개 = 혈압 2 + 특이사항 3 → 위험 recall 8/13 = 61.5% | 혈압 임상 임계값 없음, 특이사항 risk 규칙 없음 |
| test 30건 | 5개(복약 2, 낙상 1, 특이사항 2 = gs-059·gs-060, S2 복약은 복원 불가) | 헤드라인(R3·G1 제외) 3개 중 gs-059 특이사항 → 2/3 | 특이사항 risk 규칙 없음 |

- 즉 **Rule Engine(수치 임계값)과 Sentinel(텍스트 위험 신호)이 각각 한 조각씩**이다. dev의 5개 공백은 혈압 2 + 특이사항 3으로 정확히 나뉜다.

**특이사항 값이 있는 케이스**(정답 기준)

| 분할 | 특이사항 있음 | risk | ok | 없음(음성 대조) |
|---|---|---|---|---|
| dev | 11 | 3 (gs-017 엉덩이 통증 호소, gs-018 발음 어눌·왼손 힘 약함, gs-058 흉부 답답함·호흡곤란) | 8 (무릎 통증 ×2, 측정·확인 누락 ×2, 미끄러질 뻔, 낙상 후 놀람, 첫 혈압 높음, 복약 거부) | 19 |
| test | 6 | 2 (gs-059 발 부종·사흘째 식사 거부, gs-060 팔의 멍·보호자 방문 시 위축, **R3는 현장 검토 대기**) | 4 (미측정·재측정 예정, 복약 거부·맥박 누락, 기분 변화, …) | 24 |

- 위험 양성이 전체 60건 중 **5건뿐**이고 dev에는 3건이다. 규칙의 recall을 통계적으로 말하기에는 증거가 지나치게 얇다.
- 모델의 특이사항 **기록 자체**는 대체로 된다(gs-059의 "발 부종, 사흘째 식사 거부"는 모델이 기록했다). 빠진 것은 위험 **표시**다. 그래서 규칙은 "기록 내용 분류"와 "transcript 직접 스캔" 둘 다 가능해야 한다(모델이 기록을 빠뜨려도 잡도록).

## 2. 구조
```
transcript ─┬→ Extractor (LLM) ─ 필드 ─┬→ Flagger(현재: 범위·후보·복약·낙상)
            │                           ├→ Rule Engine(YAML): 수치 임계값·필드 간 규칙 → flag/이유
            └→ Sentinel(규칙 우선): 문장 단위 위험 어휘 + 가드 → signals[]
                                       └→ (선택, 2단계) LLM 보조: 규칙이 못 본 표현을 인용 근거와 함께 제안
                    Consensus(코드): 필드 flag = max(Flagger, Rule Engine, Sentinel)  ※ 올리기만 하고 내리지 않는다
```
- 모든 규칙은 flag를 **올리기만** 한다(KR-1 Flagger와 같은 원칙). 값은 바꾸지 않는다.
- Sentinel 출력은 `signals[]`: `{rule_id, category, severity, quote, provisional}`. `quote`는 transcript의 **부분 문자열**이어야 하고(검수 화면에 그대로 표시), 아니면 버린다.
- `special_notes`의 flag = risk, 조건: signals에 severity=risk가 하나라도 있을 때. Extractor가 특이사항을 비웠는데 signal이 있으면 값은 비운 채 flag만 risk + 이유 "기록되지 않은 위험 신호"로 올린다(사람이 확인).
- 규칙은 YAML로 둔다(버전, 근거 정책 행, `provisional`, 현장 확인 필요 표시).

```yaml
# rules/sentinel.yaml (스케치)
version: 1
rules:
  - id: neuro_speech
    category: 신경·의식
    severity: risk
    provisional: true           # label-policy 특이사항 risk 기준표(임시, 현장 확인 필요)
    patterns: ['말[이씀]?[이은]?\s?(?:평소보다\s)?(?:어눌|꼬이|막히)', '발음[이]?\s?(?:어눌|이상)']
    guards: [negation, conditional_advice, third_party, past_event]
  - id: intake_refusal_days
    category: 식사·수분
    severity: risk
    patterns: ['(?:이틀|사흘|나흘|[2-9]\s?일)\s?(?:째|동안|연속)…(?:거부|안\s?드|못\s?드)']
    guards: [negation, conditional_advice, third_party]
```

## 3. 규칙 범위 (정책 표 → 규칙)
정책 `docs/label-policy.md` "특이사항 risk 기준"의 6개 분류를 그대로 옮긴다(임상 기준이 아니라 **보고 우선순위용 임시 목록**).

| 분류 | 규칙 요지 | 가드 필요 |
|---|---|---|
| 흉부·호흡 | 가슴 답답·통증, 숨이 차다·호흡곤란 | 부정, 조언·가정, 제3자 |
| 신경·의식 | 말이 어눌, 한쪽·팔·손 힘 없음, 의식 흐림, 얼굴 한쪽 처짐 | 부정, 제3자 |
| 낙상 후 | 낙상 보고(앞선 2문장 안에 긍정형)와 통증·부기·거동 불편이 이어짐 | **낙상 부정형("넘어지신 적은 없다")과 구분** |
| 식사·수분 | 사흘 이상 식사·물 거부(기간 표현 필수) | 기간 없는 "오늘 안 드셨다"는 제외 |
| 신체 변화 | 발·다리·얼굴이 붓다, 출혈, 깊거나 곪은 상처 | 부정 |
| 정황(학대 의심) | 멍 여러 군데, 폭행 언급, 보호자 방문 시 위축 | **현장 확인 필요(R3): 임시 severity=risk, 전문가 검토 전에는 `needs_expert` 표시** |

**가드(오탐 방지)** — 정책 "목록에 없으면 ok"를 코드로:
- 부정: 증상 서술어 바로 뒤 "~지는 않", "~지 않"(문장 속 다른 "안"과 구분).
- 조언·가정: "혹시 가슴이 답답하면 연락 달라고…"(N4형).
- 제3자: 남편·가족·옆집의 증상(D3형).
- 과거: "작년", "몇 달 전" 등 오래된 사건(낙상은 최근 7일 정책).
- 만성 통증(무릎·허리 쑤심)은 위험 규칙에 넣지 않는다(정책: ok).

## 4. Rule Engine: 수치 임계값 (혈압·맥박)
- 현재 Flagger의 범위 규칙은 "생리적으로 불가능한 수치"(STT 오인식 탐지)일 뿐 임상 위험이 아니다. 고혈압 risk는 임시값이다: **수축기 ≥ 160 또는 이완기 ≥ 100 → risk**(provisional).
- 골든셋 혈압 값 45개 중 이 규칙과 정답 flag가 **45/45 일치**하지만, 고혈압 값이 gs-017(160/100), gs-018(170/105) 두 개뿐이고 경계 영역(150대 수축기, 90대 후반 이완기)에 정답 사례가 없다. **임계값은 데이터로 결정되지 않는다.** 임상 기준(고혈압 단계, 저혈압, 맥박 상·하한, 연령·약 복용에 따른 보정)은 **현장 전문가 확인 필요**이며, 이 설계는 값을 정하지 않고 YAML의 `provisional` 값으로만 둔다.
- 필드 간 규칙 예: 낙상 "있음"과 특이사항 통증이 함께 있으면 낙상 flag에 이유를 붙인다(이미 risk). 미복용이면서 고혈압이면 우선순위 상승(Sentinel 우선순위, 2단계).
- Sentinel의 "최근 타임라인"(상태 변화·추세)은 데이터 모델이 아직 없어 이 설계 범위 밖이다(blueprint D는 제외 범위).

## 6. test는 이 규칙의 독립 평가가 될 수 없다
- 정책 표의 "식사·수분: 사흘 이상 식사 거부", "신체 변화: 발·다리가 갑자기 붓는다", "정황: 멍·보호자 방문 시 위축"은 **test 케이스 R2·R3의 스펙에서 만든 행**이다. 규칙이 표를 따르면 test의 양성 2건은 만들어질 때부터 포착된다.
- 이번 설계는 test 케이스의 transcript를 열어 보지 않았고(현황은 정답 라벨과 스펙 수준만), 프로토타입 평가는 dev에서만 했다. 그래도 위 이유로 **test는 새 규칙의 일반화 증거가 아니다.** 새 규칙에 대한 test 점수는 "오염됨"으로 표시한다.
- 따라서 독립 평가용 **새 케이스**가 필요하다(7장).

## 7. 평가 계획 (구현 후)
1. **단위 테스트(무료, 결정적)**: 분류별 양성 문장과 어려운 음성 문장(부정, 조언·가정, 제3자, 만성 통증, 과거, 낙상 부정형, 기간 없는 식사 거부)을 각 최소 10개, 총 60개 이상. 합성 문장이라 규칙 정합성만 증명한다.
2. **새 위험 신호 골든 배치(R-set)**: 양성 20(6개 분류 고루, 표현 변형) + 어려운 음성 20(위 가드 대상 포함) = 40건. 기존 파이프라인(스펙 → Opus 생성 → 자동 점검 → 블라인드 라벨링)을 쓴다. 분할: 설계용 dev 20 / 최종 test 20. 정답과 정책은 **생성 전에** 확정한다. 비용 추정: 이전 test 23건 생성이 건당 약 $0.07이므로 40건 약 $2.8(재시도 포함 $1.5~3.7), 블라인드 모델 라벨러 약 $1, 사람 라벨링과 현장 검토는 별도. **정확한 추정은 스펙 작성 후 dry-run으로 낸다.**
3. **지표**: 특이사항 risk recall(분류별 포함), risk 아닌 케이스의 오발동률(검수 부담), 사람이 보는 알림 수. 신뢰구간 보고, 양성 20건이라 recall 구간이 넓다(예: 19/20 → 95% 구간 하한 약 76%).
4. **사전 등록 판정**: 규칙을 dev R-set으로만 조정하고, test R-set에서 한 번 실행한다(기존 동결 규칙과 같다). 이 규칙이 오탐으로 검수 부담을 얼마나 늘리는지(오발동률)를 recall과 함께 보고한다.
5. **LLM 보조(2단계, API 필요, 별도 승인)**: 규칙이 못 본 표현("몸이 이상하다", "자꾸 쓰러질 것 같다고")을 구조화 출력으로 제안하고 인용이 transcript에 없으면 버린다. 규칙만 대 규칙 ∪ LLM을 dev R-set에서 비교(Haiku 건당 약 $0.001이라 40건 약 $0.04~0.1).

## 8. 안전·윤리 주의
- 이 규칙은 진단이 아니다. UI에는 "의심", "진단" 같은 단정 표현을 쓰지 않고 "보고 확인 필요"만 쓴다. 최종 판단은 사람(사회복지사)이다.
- 놓침(위험 신호를 ok로 내보냄)이 오탐보다 해롭다. 임계값·어휘는 recall을 우선하되 오탐이 검수 부담을 키우므로 둘 다 보고한다.
- 정황(학대 의심) 규칙은 법적 보고 의무와 기관 절차가 얽혀 있다. **전문가(R3 검토자)가 기준을 확정하기 전에는 `needs_expert` 표시로 두고 자동 보고·알림으로 연결하지 않는다.**
- 전 항목이 `provisional`(임시)이다. 현장 확인으로 바뀌면 YAML 버전을 올리고 골든셋 개정 절차(v2.2 등)를 따른다.

## 9. 구현 순서 (승인 후, API 없음 → 있음)
| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | `rules/sentinel.yaml` 스키마와 로더, 가드 구현(부정·조언·제3자·과거) | 단위 테스트 60개 이상, 기존 450+건 불변 |
| 2 | Sentinel을 Flagger와 합치는 Consensus(flag = max) 연결, `special_notes` risk와 "기록되지 않은 위험 신호" | 러너에서 특이사항 risk recall 계산, F1 불변(flag만 올림), 과다 확인·조용한 오답 지표 불변 확인 |
| 3 | Rule Engine 수치 임계값 YAML(`provisional`) | 골든셋 혈압 45개와 정답 일치, 경계값 단위 테스트 |
| 4 | dev·test 재채점(캐시, 비용 0): 위험 recall 2/3·8/13이 어떻게 바뀌는지 | 결정 로그에 **test는 오염됨**으로 표시해 기록 |
| 5 | R-set 스펙 작성 → dry-run 비용 → 승인 후 생성·라벨링 (별도 설계·승인) | 독립 평가 |

## 10. 지금 말할 수 있는 것과 없는 것
- 있다: 공백의 정체(혈압 임계값 2건 + 특이사항 3건이 dev, 특이사항 1건이 test 헤드라인), 정책 표만으로 dev 3건을 오탐 없이 잡는 규칙 스케치, 오탐을 만드는 구체적 패턴(무릎 통증, 맞춘 안경, 문장이 갈린 낙상 후 통증).
- 없다: 일반화된 recall(증거 양성 5건, 모두 정책 표의 씨앗), 임계값의 임상적 타당성, 정황 규칙의 현장 타당성, LLM 보조의 이득.

## 구현 메모 (2026-10-27)
- 위치: `rules/sentinel.yaml`(규칙), `src/carenote/extraction/sentinel.py`(로더·가드·엔진), `flagger.py`(Consensus 연결), 테스트 `tests/test_sentinel.py`(100개).
- Consensus는 설계의 "max"가 아니라 기존 Flagger 우선순위를 따른다: **확인 필요 > risk > ok**. 규칙은 ok만 risk로 올리고, 확인 필요(후보 둘 이상, 불가능 수치, KR-1)는 risk에 밀리지 않는다. 사람 확인이 이미 걸린 필드를 덮지 않기 위해서다.
- 설계 대비 추가: 가드 `past_event`(식사·신체 변화 규칙에만 적용). 프로토타입에는 없었고 단위 테스트(과거 사건 음성)를 쓰며 넣었다. 규칙 정합성 외의 근거는 없다.
- 테스트가 찾은 규칙 결함: "힘이 빠져서"의 활용형(빠져)을 놓쳤다. `빠[지져]`로 고쳤다.
- 기본 동작 불변: `FlaggingExtractor(inner)`와 `flag_field(field, transcript)`는 `rules`를 주지 않으면 이전과 같다. 기존 470개 테스트 통과.
- CLI `--sentinel`은 dev 분할의 LLM 실행에만 허용한다(test·all, oracle·null은 거부). test 케이스는 평가에 쓰지 않는다. 테스트도 test 분할을 읽지 않는다.
- 현재 규칙의 dev 결과(프로토타입 재현): 특이사항 risk 3/3, 위험 아닌 케이스 오발동 0. 혈압 임계값은 dev 혈압 값과 정답 flag가 모두 일치. 둘 다 튜닝에 쓴 dev라 독립 증거가 아니다.
- 아직 없음: 수치 임상 타당성, 정황 규칙의 현장 타당성, 독립 평가(R-set).
