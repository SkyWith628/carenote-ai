# 실행 간 변동 측정 설계 (구현 전, API 호출 없음)

배경: 프롬프트 v2와 v3는 기분 규칙 두 줄만 다른데 dev 4구성에서 다른 케이스의 오류가 필드 몇 개씩 바뀌었다(`docs/decisions.md` v3 실측). 이 모델들은 temperature를 지정할 수 없어서(`extractor-design.md` 5장) **같은 입력·같은 프롬프트도 결과가 달라진다.** 현재 부트스트랩 구간은 케이스 재표집만 반영하므로 실행 간 변동만큼 구간이 좁게 나온다. 이 변동 폭을 모르면 +1%p 안팎의 프롬프트 개선(v4 등)을 판단할 수 없다.

## 1. 무엇을 재는가
| 양 | 정의 | 쓰임 |
|---|---|---|
| 실행 간 F1 표준편차 σ_run | 같은 (모델, 변형, 프롬프트, dev 30건)를 K번 돌린 F1의 표준편차 | 노이즈 바닥. 이보다 작은 F1 차이는 신호로 안 읽는다 |
| 쌍별 평균 \|ΔF1\| | 실행 쌍마다 F1 차이의 평균 | σ_run의 직관적 표현 |
| 불안정 필드 비율 | 필드 240개(30건×8) 중 K번의 정오가 **한 번이라도 다른** 필드의 비율 | 잡음이 어디서 나오는지(어떤 필드·케이스) |
| 안정 오류 vs 불안정 오류 | K번 모두 틀린 필드(안정 오류) / 일부만 틀린 필드 | 안정 오류만 프롬프트·정답·STT 구조 문제의 진짜 후보. 불안정 오류는 반복하면 사라질 수 있다 |
| 다수결 F1 | 필드마다 K번 중 다수 결과로 채점한 F1 | 노이즈를 줄인 비교 기준 |

## 2. 방법
1. **캐시 우회**: 현재 캐시 키는 `(모델, effort, 변형, 프롬프트 버전, transcript)`라 같은 입력은 같은 결과를 돌려준다. `--run-tag N`(기본 없음)을 추가해 태그가 있을 때만 키에 포함한다. 태그가 없는 기존 실행과 캐시는 그대로 유효하고, 기존 v2·v3 실행이 **run 0**으로 쓰인다.
2. **보고서에 필드 단위 결과 저장**: 지금 `per_case`는 TP/FP/FN 합계라 필드별 안정성을 못 본다. `per_field`(케이스·필드별 `tp|fp|fn|fpfn|tn`)를 보고서 JSON에 더한다(추가 항목, 기존 읽기 호환).
3. **분석 도구** `python -m carenote.evaluation.variance A.json B.json ...`: 같은 구성의 보고서 여러 개를 받아 σ_run, 쌍별 |ΔF1|, 불안정 필드 목록, 안정 오류, 다수결 F1을 출력.
4. **프롬프트 간 비교의 새 판정 규칙(결과를 보기 전에 정함)**: 프롬프트 X가 Y보다 낫다고 쓰려면 둘 다 K번 실행하고 (a) 평균 F1 차이가 두 프롬프트의 σ_run 합성값의 2배보다 크고, (b) 케이스를 재표집한 **실행 평균 결과**의 95% 구간이 0을 포함하지 않아야 한다. 하나라도 아니면 "구분 불가"로 쓴다.
5. 실행 횟수 K: 한 구성에서 σ를 추정하려면 최소 4~5번이 필요하다(표준편차 추정의 상대 오차 약 ±35%, K=5 기준). 기존 run 0 + 추가 4번 = 5번.
6. **dev만 쓴다.** 변동 측정에 test를 쓰지 않는다(동결 규칙).

## 3. 비용 추정 (API 없음)
측정된 1회(30건) 실제 비용: Haiku B0 약 $0.0205, Haiku B1 약 $0.0275, Sonnet B0 약 $0.285, Sonnet B1 약 $0.36. 게이트 최대 추정치는 실제의 약 3.4~5배이고(Haiku $0.07, Sonnet $1.40) 실행마다 별도로 승인한다.

| 단계 | 내용 | 호출 | 예상 실제 비용 | 승인액(실행당) |
|---|---|---|---|---|
| **1 (권장)** | Haiku B0·B1 × 프롬프트 v2·v3 × 추가 4회 = 16회 | 480건 | **약 $0.39** (B0 8회 $0.165 + B1 8회 $0.22) | 0.07 / 0.08 |
| 1 축소판 | Haiku B1 × v2·v3 × 추가 4회 = 8회 | 240건 | 약 $0.22 | 0.08 |
| 2 (선택) | Sonnet B1 × v2·v3 × 추가 2회 = 4회 | 120건 | 약 $1.45 | 1.40 |
| 합계 | 1 + 2 | | 약 $1.84 | |

- 1단계만으로 "Haiku에서의 σ_run"과 "어떤 필드가 불안정한가"를 알 수 있다. Sonnet은 같은 크기의 변동이 있다고 가정하지 않고, 필요하면 2단계로 확인한다(Sonnet은 8~13배 비싸다).
- 추정은 이전 실측 비용을 그대로 곱한 것이다. 출력(추론) 토큰이 실행마다 달라 ±20% 흔들릴 수 있다.
- 지연: Haiku 1회 약 2~3분(B1이 더 김), 16회 순차 실행 시 약 40~50분. 한 실행씩 `--approve-cost`로 승인하므로 중간에 멈출 수 있다.

## 4. 구현 순서 (승인 후, 모두 API 없이 테스트)
| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | `--run-tag` (캐시 키, `usage_summary`, 보고서 기록) | 태그 없음이면 기존 캐시 키 불변(테스트), 태그가 다르면 캐시 분리 |
| 2 | 보고서 `per_field` 추가 | oracle/null/가짜 클라이언트 보고서에서 필드별 결과 합이 `per_case`와 일치 |
| 3 | `evaluation.variance` 도구 | 합성 보고서 3개로 σ, 불안정 필드, 다수결 F1 단위 테스트 |
| 4 | 기존 run 0 보고서 재생성 | v2·v3 Haiku 보고서를 캐시로 재채점해 `per_field` 포함(비용 0) |
| 5 | 1단계 실측 | 실행마다 승인액 지정, 결과를 결정 로그에 기록 |

## 5. 한계와 위험
- K=5의 σ 추정은 거칠다. "프롬프트 효과 ≥ 2σ" 규칙은 보수적이어서 +1%p 효과는 여전히 구분되지 않을 가능성이 높다. 그것이 정직한 결론이다: **dev 30건으로는 +1%p를 판정할 수 없고, 목표 필드 단위 판정(예: gs-002 기분이 고쳐졌는가)이 더 신뢰할 만하다.**
- 불안정 필드는 대개 특이사항(자유 문장 유무)과 기분(추론 경계)에 몰릴 것으로 예측한다. **예측**이며 측정으로 확인한다.
- 반복 실행은 같은 모델의 변동만 잰다. 모델 버전 변경, 프롬프트 캐시 상태, 서버 부하는 반영하지 않는다.
- 비용 누적: 이 설계의 1단계는 지금까지 평가 실행 누계(약 $1.9)의 약 20%다.
