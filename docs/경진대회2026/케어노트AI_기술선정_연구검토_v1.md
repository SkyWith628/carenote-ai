# 케어노트AI 기술선정·연구 검토 v1

작성일: 2026-09-18

대상: 경진대회 기획서 v2, 기존 음성녹음 기능설계, 현재 코드 골격.
성격: 기술 선택을 위한 조사·권고 문서. 구현 완료나 실측 성능 보고가 아니다. 기획서의 확정 결정을 대체하지 않는다.

## 1. 결론과 우선순위

**기존 웹·서버·사람 승인 구조는 유지하고, 사실 구조화와 원음 추적을 보완한다. STT는 Whisper를 기준선으로 Qwen3-ASR과 비교하고, 교체는 자체 평가 후 결정한다.**

현재 `services/api/pyproject.toml`, `app/stt/transcribe.py`, `app/agents/graph.py`는 TODO 골격이고 `apps/web/package.json`은 빈 객체다. 따라서 ‘기존 기술 유지’는 검증된 운영 시스템 유지가 아니라 설계 방향을 유지한다는 뜻이다. 이미 작동하는 그래프가 있어 그대로 재사용할 수 있다는 과거 문구는 현 상태를 설명하지 못한다.

| 영역 | 권고 | 얻는 것 | 대가·제약 | 변경을 결정할 근거 |
|---|---|---|---|---|
| 모바일 웹 + FastAPI | 유지 | 녹음·승인 흐름 구현 범위가 명확함 | 모바일 녹음 호환성 확인 필요 | 실제 기기 과업 테스트 |
| STT | faster-whisper 기준선 유지, Qwen3-ASR 비교 | 한국어 인식 개선 가능성 | 새 런타임·메모리·설치 부담 | 핵심 사실 오류와 검토시간 감소 |
| 전처리 | VAD와 무음 입력 차단 추가 | 비발화 구간에서 생성되는 오류를 줄일 가능성 | 작은 목소리·말끝을 잘라낼 수 있음 | VAD 전후 사실 누락률 |

| 불확실성 | 단일 confidence 대신 구간별 검토 신호 | 확인할 위치를 설명할 수 있음 | 임계값 조정·오탐 관리 | 오류 탐지율과 검토 부담 |
| 규정 RAG | 작은 양식·규칙 패키지부터, 검색 확장은 조건부 | 규정과 관찰 사실의 혼동 감소 | 문서 버전 관리 필요 | 필요한 규정 검색 실패가 발생하는가 |
| LangGraph | 필수에서 선택으로 | 작은 워크플로의 구현 단순화 | 상태·재시도 관리 책임은 남음 | 재개·분기 복잡도와 동일조건 지연 비교 |
| 파인튜닝 | 기준선 이후 별도 실험 | 특정 오류·출력 양식 개선 가능성 | 정답 데이터·GPU·회귀평가 필요 | 프롬프트·규칙보다 추가 개선되는가 |
| 다중 에이전트·자율 브라우저 | 대회 핵심 범위에서 보류 | 호출·실패 경로 감소 | 유연한 자율작업은 제한됨 | 현재 단일 기록 업무에는 필요성 미확인 |

우선순위는 ① 사실·근거 스키마 ② 원음으로 돌아가는 검토 UI ③ STT 비교 ④ 오류·시간 평가 ⑤ 필요한 경우 RAG·파인튜닝 순이다. 이 우선순위는 아래 자료를 바탕으로 한 프로젝트별 판단이며 논문이 직접 입증한 순위가 아니다.

## 2. 기존 기획에서 바로잡아야 할 기술적 가정

### 2.1 내부 서버 처리와 온디바이스는 다르다

휴대폰에서 녹음하고 서버에 업로드해 faster-whisper를 실행하면 **자체 서버 STT**다. 휴대폰 안에서 추론해야 온디바이스다. 기존 문서의 ‘로컬/온디바이스(서버 내부)’와 ‘음성은 외부로 절대 안 나감’은 구분해야 한다.

권고 표현: ‘음성은 지정된 자체 처리 서버로 전송하고, 외부 STT 서비스에는 전달하지 않는 구조를 설계한다.’ 내부 처리도 접근통제·보관·삭제 구현이 필요하다. 이번 검토는 법적 적합성을 판정한 것이 아니다.

### 2.2 STT confidence는 사실이 맞을 확률이 아니다

faster-whisper는 단어별 정보와 타임스탬프 등을 제공한다[S1]. 이 값의 임계치만으로 ‘발음·사투리 오류를 자동 판별한다’고 약속해서는 안 된다. 높은 점수로 잘못 인식할 수 있고, 모델별 점수도 직접 비교하기 어렵다.

권고: 구간별 인식 점수, 숫자·부정 표현, 누락 필드, 사용자 수정 기록을 각각 저장한다. 화면에는 ‘정확도 95%’ 대신 ‘시간 확인 필요’처럼 이유를 표시한다. 경고 기준은 개발셋에서 조정하고 별도 테스트셋에서 탐지율·오탐률을 확인한다.

### 2.3 전사문과 일치해도 원음과는 다를 수 있다

STT가 ‘안 드셨다’를 ‘드셨다’로 바꾸면 LLM은 틀린 전사문을 충실하게 문서화할 수 있다. 따라서 **전사 정확성(원음 대 전사문)**과 **초안 충실성(전사문 대 초안)**을 분리하고, 최종 초안도 원음 기준으로 평가한다. Whisper의 비발화 구간 환각 연구는 이 첫 번째 오류 경로를 다룬다[R1].

### 2.4 원문에 없던 조치를 완료 사실로 쓰지 않는다

현재 기획서 예시의 ‘상태 재확인 및 보호자 공유가 필요함’은 원문 관찰 사실과 성격이 다르다. 초안에는 원문에서 확인되는 식사·어지러움 사실을 기록하고, ‘보호자에게 공유했나요?’는 확인 질문으로 분리한다. AI가 제안한 조치를 ‘공유함’으로 저장하지 않는다.

### 2.5 프레임워크·사람 승인에 관한 과장도 피한다

‘LangGraph를 쓰면 엄청 느리다’는 일반 결론을 이번 자료에서 확인하지 못했다. 호출 횟수, 출력 길이, 모델 추론, 대기열, 체크포인트 쓰기를 나눠 측정해야 한다. 사람 승인 역시 오류를 모두 잡는 보장은 아니다. 과신·반복 경고로 놓치는 사례를 사용성 평가에 포함한다.

‘중요 오류 100% 탐지’는 알려진 테스트 규칙의 통과 조건으로 제한하고, 실제 현장의 모든 오류를 보장하는 문구로 쓰지 않는다.

## 3. 음성인식 후보와 교체 판단

### 기준선: faster-whisper + Whisper large-v3 / turbo

faster-whisper는 모델 이름이 아니라 Whisper를 실행하는 CTranslate2 기반 구현체다. 공식 저장소에 turbo 실행, 단어 타임스탬프, Silero VAD 사용 예시가 있다[S1]. 먼저 turbo와 large-v3를 동일 녹음·동일 장비에서 비교한다. GPU가 제한되면 작은 다국어 모델이나 양자화를 별도 조건으로 시험한다.

유지 이유는 기존 설계와 연결하기 쉽고 원음 구간 재생에 필요한 시간 정보를 얻기 쉽다는 점이다. 공식 저장소의 속도 수치는 장비·배치·설정이 달라 우리 성능으로 인용하지 않는다. STT 용어 프롬프트 역시 정답 강제 기능이 아니므로 용어 미발화 시 잘못 삽입되는지 검사한다.

### 신규 비교 후보: Qwen3-ASR-0.6B / 1.7B

2026년 기술보고서와 공식 모델카드는 한국어 지원, 두 모델 크기, 공개 가중치를 명시한다. ForcedAligner도 한국어를 지원하지만 추가 모델 실행이 필요하다[R2, S2]. **공식 목록의 방언 지원은 한국어 지역 사투리 성능 보장이 아니다.**

- 0.6B: 작은 후보로 먼저 설치·지연·메모리 실측.
- 1.7B: 자원이 허용되면 품질 비교 후보로 추가.
- 타임스탬프가 필요한 경우 aligner 포함 총지연과 메모리를 비교.
- 모델카드의 고동시성 처리량을 모바일 사용자의 단건 대기시간으로 해석하지 않음.
- 별도 실행 환경에서 시험하고 채택 시 체크포인트 revision과 의존성을 고정.

Qwen3-ASR 교체 조건은 평균 CER 개선뿐 아니라 **부정·시점·숫자·실시 여부 오류가 줄고, 검토시간과 운영 부담이 허용되는 것**이다. 작은 데이터에서 근소한 차이가 나면 즉시 교체하지 않는다.

### 조건부 보완

항상 두 STT를 실행하는 앙상블은 비용·지연을 늘린다. 필요하면 의심 구간만 두 번째 모델로 재전사해 불일치를 표시한다. 두 모델의 일치는 진실 보장이 아니며 모델 간 오류도 상관될 수 있다.

VAD는 발화 구간 검출이지 범용 잡음 제거기가 아니다. 소음 제거 모델도 음소를 손상할 수 있으므로 기본 도입하지 않는다. MVP는 요양보호사 한 명의 사후 메모 녹음을 가정하므로 다화자 분리와 상시 대화녹음도 보류한다.

## 4. 초안 생성: 모델보다 중간 표현을 먼저 설계

추천 첫 비교는 아래 두 방식이다.

- 기준선 A: 전사문 → LLM이 양식 전체를 직접 생성.
- 보완안 B: 전사문 → 사실 JSON → 필수항목·일관성 검사 → 양식 렌더링.

처음에는 사실 추출에 LLM을 한 번 호출하고, 문장은 템플릿으로 출력한다. 문장 품질이 실제 검토를 방해할 때만 두 번째 문장화 호출을 추가한다. 연구 R3의 사실 단위 평가와 R5의 항목 간 일관성 분석을 설계 참고로 사용한다. 해당 논문이 이 B 방식을 한국어 방문요양에서 검증한 것은 아니다.

### 최소 사실 스키마 제안

```json
{
  "fact_id": "f1",
  "subject_id": "selected_recipient",
  "field": "meal_intake",
  "value": "점심을 거의 먹지 않음",
  "polarity": "negative",
  "event_time": "unknown",
  "evidence": {"segment_id": "s1", "quote": "점심 거의 안 드시고"},
  "action_status": "not_applicable",
  "review_status": "pending"
}
```

source segment에는 원음 시작·종료시간을 보관한다. 인용 구절이 실제 전사문 안에 존재하는지는 코드로 확인한다. 인용이 존재한다는 것과 해석이 맞다는 것은 별도로 평가한다. 수급자 식별은 사용자가 선택한 ID를 사용하고 음성 속 이름으로 자동 확정하지 않는다.

JSON Schema는 형식·타입·필수항목을 검사한다. 사실의 진위를 보장하지 않는다. 필드값이 없으면 `unknown`으로 남기고, 이전 기록이나 규정으로 채워 넣지 않는다. 여러 필드의 날짜·수치·주체는 공통 사실 테이블을 참조하도록 한다.

### LLM 후보

| 후보 | 활용 방식 | 장점 | 도입 조건·한계 |
|---|---|---|---|
| 외부 API LLM 1종 | 마스킹된 전사문에서 사실 추출 | GPU 운영 없이 기준선 구축 가능 | 모델·버전 미확정. 비용·정보처리 조건·한국어 성능 비교 필요 |
| Qwen3-4B-Instruct-2507 | 자체 서버 추출·양식 출력 비교 | 상대적으로 작은 공개 모델 후보 | 한국어 돌봄 품질과 JSON 안정성 실측 필요 |
| Qwen3-8B non-thinking | 4B 품질이 부족하고 자원이 있을 때 비교 | 공개 모델, 비추론 모드 선택 가능 | 메모리·지연 증가, 우수성 미검증 |

공식 모델카드에서 공개 모델 후보와 모드를 확인했다[S3, S4]. 최신 최고 성능 모델이라는 추천이 아니라 범위가 작은 재현 가능한 비교 후보다. 의료 전문 모델이라는 이유만으로 우선하지 않는다. 우리 과제는 진단 추론보다 한국어 정보 추출·부정·양식 준수에 가깝다.

외부 API의 특정 제품·가격 비교는 이번 보고서 범위에 포함하지 않았다. 현재 계정에서 쓸 수 있는 모델과 자체 서버 자원이 확인되면 같은 평가표로 선택한다.

## 5. RAG: 환각 해결책으로 묶지 말고 역할을 제한

관찰 사실과 규정 근거를 서로 다른 데이터로 관리한다.

| 데이터 | 사용 목적 | 하면 안 되는 일 |
|---|---|---|
| 이번 방문 원음·전사문 | 실제 사건의 기록 | 규정에서 이번 방문 사실을 추론 |
| 과거 기록 | 비교 참고, 별도 표시 | 과거 상태·조치를 오늘 사실로 복사 |
| 양식·규정 | 필수항목·작성 기준·경고 설명 | 규정상 권장 조치를 수행 사실로 기록 |

문서 1종 MVP는 `form_id + version + effective_from + effective_to`로 양식과 필수항목을 결정적으로 조회한다. 방문일에 맞는 버전을 찾지 못하면 확인 필요로 처리한다. 적은 규칙을 항상 검색하도록 만드는 것은 불필요한 실패 경로를 늘릴 수 있다.

규정이 늘어 검색이 필요해지면 PostgreSQL·pgvector 설계를 유지하고, 키워드 검색과 BGE-M3 dense embedding을 비교한다. BGE-M3는 다국어 검색 후보이지 한국 장기요양 규정에 검증된 최적 모델은 아니다[R6, S5]. PostgreSQL 기본 전문검색을 곧바로 한국어 BM25라고 부르지 말고 토큰화·BM25 구현을 별도 확정한다.

검색 결과는 방문일·문서 종류·규정 버전 필터를 먼저 적용한다. Reranker는 Recall@k·근거 정확도에서 문제가 확인될 때 추가한다. GraphRAG, 자율 검색 반복, 다중 에이전트 검색은 현재 문서 1종에 필요한 이득이 확인되지 않아 보류한다. 검색 평가와 생성 평가를 나누는 RAGChecker의 접근을 참고한다[R7].

## 6. 앱·웹·에이전트 연결 권고

```text
모바일 웹: 녹음·업로드
  → FastAPI: 인증·작업 ID 반환
  → 작업 워커: VAD → 자체 서버 STT → 마스킹 → 사실 추출
  → 코드: 필수항목·근거·양식 검증 → 초안 저장
  → 검토 웹: 원음 구간 재생·확인 질문·수정·승인
  → 승인된 버전 저장 (선택: 데모폼 자동채움)
```

추천 상태는 `uploaded → transcribing → extracting → needs_review → approved`이며 실패 상태와 재시도 이력도 둔다. 요양보호사에게 추가 확인이 필요한 경우 별도 질문 상태를 둔다. 승인 대기 동안 HTTP 요청이나 모델 프로세스를 계속 열어 두지 않는다.

초기에는 FastAPI·DB 상태·단일 워커로 충분한지 확인한다. 다중 요청과 내구성 있는 작업 큐가 필요하면 기존 Redis 큐 구상을 적용한다. 업로드 재전송·워커 재실행이 초안 중복 생성으로 이어지지 않게 작업 ID와 멱등성을 설계한다.

LangGraph는 상태 저장·중단·재개가 실제로 복잡해질 때 도입 후보로 남긴다. 공식 문서는 체크포인트와 interrupt를 제공한다[S6, S7]. 승인 대기가 있다는 이유만으로 반드시 LangGraph가 필요한 것은 아니다. 반대로 일반 코드가 항상 빠르다고 단정할 수도 없다. 동일 모델·호출 수·저장 조건을 고정해 비교한다. Anthropic의 실무 지침도 고정 워크플로와 자율 에이전트를 구분한다[S8].

모바일 웹에서는 MediaRecorder로 녹음하고 API로 전송하며 AI는 서버에서 실행한다[S9]. 기기별 지원 MIME을 확인해 서버에서 변환하고, 화면 잠금·탭 전환·업로드 실패를 시험한다. 네이티브 앱은 이 요구가 웹으로 충족되지 않을 때 다시 판단한다.

## 7. 파인튜닝은 대상별로 구분

| 대상 | 개선하려는 문제 | 필요한 정답 | 권고 |
|---|---|---|---|
| STT | 사투리·발음·돌봄 용어 오인식 | 음성-정확한 전사 쌍 | 모델 비교·녹음 개선 후에도 반복 오류가 남을 때 |
| LLM | 사실 필드 추출·일관된 표현 | 전사문-사실 JSON 또는 승인 문서 쌍 | 프롬프트·템플릿 기준선 이후 |
| 검색 모델 | 필요한 규정 검색 실패 | 질문-관련 조항·오답 문서 | MVP에서는 후순위 |

QLoRA는 LLM 학습 메모리 부담을 줄이는 연구이며, 자동으로 정답 품질을 높이거나 한국어 STT 성능을 보장하는 방법은 아니다[R8]. LLM 경량 튜닝의 학습 실험에 활용할 수 있다. STT 튜닝은 해당 모델 구조·학습 코드 지원을 별도로 확인해야 한다.

학습·개발·최종평가를 화자와 사례 단위로 분리한다. 같은 문장을 소음만 바꿔 양쪽에 넣거나 AI가 만든 정답을 검토 없이 평가 기준으로 사용하지 않는다. 데이터 양은 학습곡선으로 결정하고 ‘몇 건이면 충분하다’고 미리 단정하지 않는다. 변경되는 규정은 모델 가중치보다 버전 관리 데이터에 둔다.

## 8. 보완 기술의 실제 적용 범위

- **원음 추적 UI:** 초안의 사실을 누르면 해당 구간 재생. 타임스탬프 오차를 고려해 앞뒤 여유 구간 제공. 모든 문장을 색칠하기보다 숫자·부정·후속조치·미확인 항목을 우선 표시한다.
- **확인 질문:** ‘보호자 공유 여부가 원문에 없습니다’처럼 양식상 필요한 미확인 필드에 한정한다. 필요하지 않은 질문까지 늘리면 시간 절감이 사라진다.
- **개인정보:** 알려진 수급자 식별정보 치환 + 전화번호 등 패턴 + 한국어 개체 탐지의 조합을 시험한다. Presidio는 확장 후보이며 설치만으로 한국어 개인정보 탐지가 완성되지 않는다[S10].
- **평가용 LLM:** 인간 평가를 보조할 수 있지만 정답 판정의 유일한 주체로 두지 않는다. R5에서는 일관성 항목별 인간-모델 일치가 달랐다. 같은 모델의 자체 재검토만으로 사실 확인을 대체하지 않는다.
- **자동채움:** 승인 버전·수급자·폼 필드를 코드로 대조하고 read-back 수행. 문서작성 효과 검증과 별도 지표로 평가하며 자율 브라우저 모델 도입은 보류한다.

## 10. 대회 전 실행 가능한 비교 실험

아래 건수·일정은 작업량을 가늠하기 위한 제안이며 통계적 충분성이나 성능 보장 수치가 아니다.

### A. 평가셋부터 고정

첫 20개 사례로 스키마·라벨 기준을 점검한다. 이어 화자 6~10명, 30~90초 정도 녹음 60~100건을 목표로 일반 발화·지역 발화·소음·긴 쉼·부정·숫자·정정 발화를 포함한다. 실제 방언 화자가 없으면 연기한 사투리를 실제 방언 성능 근거로 쓰지 않는다.

주 화자는 수급자보다 **메모를 남기는 요양보호사**다. 원음에서 사람이 작성한 전사문, 사실 목록, 필수항목 정답, 미확인 항목을 준비한다. 가능한 경우 두 평가자가 독립 주석하고 불일치는 합의한다. 개발용과 최종 시험용은 화자·사례를 분리하고 같은 사례의 소음 변형도 같은 분할에 둔다.

### B. 실험 순서

| 실험 | 고정 조건 | 바꾸는 것 | 결정 |
|---|---|---|---|
| E1 STT | 같은 음성·장비·입출력 규격 | Whisper turbo / large-v3 / Qwen3-ASR 0.6B, 여유 시 1.7B | 핵심 사실 오류와 지연으로 후보 선정 |
| E2 전처리 | 선정 STT·음성 | VAD 없음/있음, 필요 시 용어 힌트 | 말끝 손실 없이 도움이 되는가 |
| E3 생성 구조 | 사람이 검수한 동일 전사문·동일 LLM | 직접 생성 / 사실 JSON+템플릿 | ASR 영향 없이 생성 개선 확인 |
| E4 모델 | 같은 스키마·출력 길이·평가셋 | API 후보 / Qwen 4B / 자원 허용 시 8B | 품질·지연·비용 비교 |
| E5 종단 평가 | 실제 STT 출력 | 선정 파이프라인과 원음 정답 비교 | 오류 누적 확인 |
| E6 사람 검토 | 균형 잡힌 사례·참여자 | 수기 / 직접 생성 검토 / 근거 연결 검토 | 최종 수정·승인까지 총시간 비교 |

E1에서 모든 후보를 설치하지 못하면 기준선 하나와 새 후보 하나부터 비교한다. E6는 사례 순서를 교차 배치해 같은 내용을 먼저 본 학습효과를 줄인다. 검토 중 원음 청취·재녹음·되묻기 시간과 요양보호사의 추가 노동도 집계한다.

### C. 공통 지표

- CER/WER: 문자·단어 오류율. 띄어쓰기·숫자 정규화 규칙을 고정하고 원래 표기 결과도 보존.
- 중요 사실 오류: 부정, 대상자, 시간, 수치, 실제 수행 여부 각각의 오류 건수/전체 해당 항목 수.
- 근거 없는 사실 비율: 원음 정답이 지지하지 않는 생성 사실/생성 사실 전체.
- 누락률: 반드시 남겨야 할 정답 사실 중 누락된 비율.
- 경고: 실제 오류 탐지율, 경고 중 실제 오류 비율, 문서당 경고 수.
- 사용자 효과: 녹음·수정·재질문·승인 포함 총시간과 역할별 시간.
- 운영: warm/cold 지연, p50/p95, 실패율, 피크 메모리, LLM 호출·토큰 수.

희귀 오류는 분모와 함께 보고한다. 20건에서 오류 0건을 ‘정확도 100% 보장’이라고 표현하지 않는다. 새 기술은 오류 개선이 반복 확인되고 총검토시간·자원 부담이 허용될 때 채택한다. 선택 기준을 개발셋에서 정한 뒤 최종 시험 전에 고정한다.

### D. 비용과 자원

API 비용은 실제 입력·출력 토큰 × 조사 시점 단가로 산출하고, 재시도·마스킹·저장·STT 비용도 포함한다. 로컬 추론은 모델 다운로드가 무료여도 GPU 시간·서버·운영 비용이 든다. 장비가 미확정이라 VRAM·월비용을 확정하지 않았다. GPU가 부족하면 STT와 LLM을 동시 상주시킬지 순차 실행할지 먼저 실측한다.

권장 준비 순서: 9월 하순 평가셋·STT 비교 → 10월 초 사실 스키마·검토 UI PoC → 10월 중순 이전 사용자 비교·실패 사례 정리. 참여자·장비 확보 여부에 따라 범위를 줄이고, 발표에서는 계획·구현·실측을 명확히 구분한다.

## 11. 기획서에 반영할 후보 문장

| 현재 표현·가정 | 권고 표현 |
|---|---|
| 사실 단위로 확인한다 | 사실을 추출하고 원음 근거와 함께 사람이 확인하도록 돕는다 |
| 사투리·발음의 불확실성을 표시한다 | 구간별 검토 신호를 제공하고 사투리·발음 오류 탐지 성능을 평가한다 |
| 확인된 내용만 기록된다 | 미확인 항목을 표시하고 사용자 승인 후 기록한다 |
| 모든 중요 오류 탐지 | 정의된 오류 시나리오의 탐지율과 잔여 오류를 보고한다 |
| 기존 도구는 전체 과정을 지원하지 못한다 | 경쟁 조사로 확인할 차별성 가설로 남긴다 |
| 로컬/온디바이스 STT | 자체 서버 STT와 휴대폰 내 추론을 구분한다 |

대회용 기술 메시지 제안: **‘음성을 매끄럽게 요약하는 데서 그치지 않고, 기록의 각 사실을 원음에 연결해 사회복지사의 확인과 수정을 돕는다. 그 효과는 기존 작성 방식과의 시간·오류 비교로 검증한다.’**

남은 결정은 양식 1종, 실제 입력·확인 책임자, 사용 가능한 GPU, 현장 녹음 확보 여부다. 이 정보가 정해지기 전에는 한국어 최고 모델·사투리 해결·시간 절감률·안전성 보장을 확정하지 않는다.
