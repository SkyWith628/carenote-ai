# v4 ablation 설계: gs-003 혈압 하락의 원인 찾기 (도구 구현 완료, 실측 전)

> 구현 상태(2026-10-26): `--prompt-edits`, `--case-ids`, `evaluation.ablate` 구현과 테스트 완료(API 없음). 실측은 아직 하지 않았다.
> 사용법: `python -m carenote.evaluation.ablate --extractor llm-b1 --model claude-haiku-5-5 --targets gs-003:blood_pressure --variants v3 v4 --runs 20 --dry-run` 후 `--approve-cost`. 변형 표기 `v3` · `v4` · `v4-drop:N` · `v4-only:N` · `v4-edits:1,3`.
> 구현에서 정한 것: 반복은 변형을 번갈아 돌려 중간에 멈춰도 균형이 맞고, 비용 한도에 닿으면 거기까지의 결과 표를 보여 주고 종료 코드 3으로 멈춘다(끝난 호출은 캐시에 남아 같은 명령으로 이어서 진행). 각 반복은 서로 다른 `--run-tag`(ab1~abN)를 쓴다.
> **승인액은 도구의 dry-run 추정 최대 이상이어야 시작한다**(아래 4장의 승인액 제안 $0.10, $0.20은 실제 dry-run 추정 최대보다 작아 거부된다. 정정된 값: 단계 0 $0.093 → 승인 $0.10, 단계 1(v3·v4 기준 포함 7변형 140회) $0.326 → 승인 $0.33). 예상 실제 비용은 4장 그대로다(약 $0.04, 약 $0.13).

원래 설계(구현 전):

배경: v4 측정(`docs/decisions.md` 2026-10-26)에서 사전 목표 밖의 **gs-003 혈압**이 v3 대비 B1 3/5 → 0/5, B0 3/5 → 1/5로 떨어졌다(하락 p 0.083, 0.262, 탐색적 점검). 질문 "백삼십 팔십이었나, 아니 백사십 팔십이었나"는 번복이 풀리지 않아 정답이 후보 두 개 + 확인 필요인데, v4 B1은 5회 모두 "140/82"로 확정했다(flag ok). v4는 v3 위에 5곳을 바꿨다.

| 편집 | 내용 | gs-003 혈압과의 관련 가설 |
|---|---|---|
| E1 | 식사 매핑: "못 드심·안 드심(정도 없이)=미섭취" | 낮음 (혈압과 무관) |
| E2 | 숫자 한 글자씩 읽기 새 예시 `일삼오 → 135`, `칠오 → 75` | **가장 높음**: 수치를 확정 숫자로 옮기라는 암시가 강해져 모호한 숫자도 확정할 수 있다. "팔십이었나"의 "이"를 숫자 2로 읽어 82를 만든 점도 숫자 변환과 맞는다 |
| E3 | 복약 필드 이유·정황은 특이사항에 중복 금지 | 낮음 |
| E4 | 특이사항 (b)에 "잊었다·기억 못 한다", "확인·질문을 못 한 항목" | 낮음~중간: "기억 못 함" 문구가 번복·불확실 처리 경로에 영향을 줄 수 있다 |
| E5 | 정책 #14 (오늘 복약 직접 확인만) | 낮음 |

위 가설 순위는 **측정 전 예측**이다. 어느 것도 확인하지 않았다. 편집 전체가 프롬프트 길이·구조를 바꾸는 부수 효과나 단순 노이즈일 수도 있다.

## 1. 핵심 아이디어: 한 케이스만 많이 반복한다
gs-003 혈압 하나만 보면 되므로 30건 전체를 돌릴 필요가 없다. 한 건의 호출은 Haiku B1에서 약 $0.0009, B0에서 약 $0.0007이다. 같은 케이스를 같은 프롬프트로 **20번** 호출하면 정답 비율을 5회짜리보다 훨씬 좁게 추정할 수 있다(20회: 정답률 60% 대 10%는 피셔 p ≈ 0.01).

## 2. 단계 (앞 단계 결과로 다음 단계를 정한다)
### 단계 0: 하락이 실재하는가 (약 $0.04)
- v3와 v4를 gs-003 하나로 각 20회(B1). 정답 횟수를 피셔 단측으로 비교.
- **사전 규칙**: v4가 v3보다 낮고 p ≤ 0.05이면 하락은 실재 → 단계 1. 아니면 **노이즈로 결론**하고 ablation을 접는다(v4 채택은 사전 기준대로 진행하되 gs-003을 불안정 필드로 기록).
- 이 단계가 먼저인 이유: 5회짜리 하락의 p가 0.083이라 노이즈일 가능성이 크고, 그러면 나머지 비용이 낭비된다.

### 단계 1: 한 개씩 빼기 (leave-one-out, 약 $0.09)
- 변형 5개: v4에서 E1만 뺀 것, E2만 뺀 것, … E5만 뺀 것. 각 20회(B1, gs-003).
- **원인 판정(사전 규칙)**: v4−Ek의 정답률이 v3와 v4의 중간값 이상이고 v4 대비 피셔 p ≤ 0.05이면 Ek는 "복원에 필요한 변경"(원인 후보). 여럿이면 가장 큰 복원 순.
- 전부 아니면 단일 원인이 없다 → 상호작용 또는 전체 부피 효과. 단계 2에서 다룬다.

### 단계 2: 하나만 더하기 (add-one, 약 $0.04~0.09)
- 단계 1의 원인 후보 Ek를 v3에 **혼자** 얹은 변형(v3+Ek)을 20회. 정답률이 v3보다 낮고 p ≤ 0.05이면 "충분 조건"으로 확정.
- 단계 1에서 후보가 없으면 E2·E4만 먼저 시도(가설 순위).

### 단계 3: 가드 케이스 확인 (선택, 약 $0.1)
- 최종 후보 프롬프트를 gs-012 방문 시각, gs-023 특이사항(다른 하락 후보)과 목표 필드(gs-008, gs-019, gs-018, gs-002)에서 각 10회 확인. v5 후보가 목표 개선을 유지하면서 gs-003이 복원되는지 본다.

### B0는 어떻게
- B1에서 하락이 더 컸으므로(3/5 → 0/5) 단계 0~2는 **B1만** 한다. 원인이 정해지면 B0에서 같은 변형 한두 개로 확인한다(단계 3에 포함).

## 3. 구현 (승인 후, API 없이 테스트)
| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | `--prompt-edits 1,3,4,5`: v4 편집 중 일부만 v3에 적용(기본은 전부 = v4). 캐시 키에 편집 집합 포함, 전부이면 키 불변 | v4와 `1,2,3,4,5`가 바이트 동일, 부분 집합마다 다른 프롬프트, 기존 v4 캐시 키 불변(테스트) |
| 2 | `--case-ids gs-003,...`: 평가할 케이스를 지정(dev만, test 포함이면 `--final-report` 필요) | 지정 케이스만 호출, test 가드 유지 |
| 3 | 반복 실행 드라이버 `python -m carenote.evaluation.ablate`: 변형 목록 × 케이스 × 반복 횟수를 **한 프로세스, 한 CostGuard**로 돌리고 정답 횟수·피셔 p를 표로 출력, 승인액에 닿으면 멈춤 | 가짜 클라이언트로 호출 횟수·비용 누적·중단·피셔 값 단위 테스트 |
| 4 | 단계 0 실행 | 승인액 지정 |

한 프로세스·누적 한도로 돌리는 이유: 호출 수백 번을 실행마다 별도 승인하면 번거롭고, 케이스 하나의 비용이 게이트 최소 단위보다 훨씬 작아 실행별 게이트가 의미가 없다. 누적 비용이 승인액에 닿으면 즉시 멈추므로 한도는 지켜진다.

## 5. 한계
- 한 케이스, 한 모델(Haiku)의 결과다. 원인으로 지목된 편집이 다른 모델·다른 번복 케이스에서도 같은 작용을 한다고 말할 수 없다. 일반화는 test 1회와 추가 번복 케이스 확인이 필요하다.
- gs-003은 dev 케이스라 이 결과로 프롬프트를 고치면 gs-003에 대한 dev 점수는 더 이상 독립적이지 않다. 개선을 말할 때 이 점을 함께 적는다.
- 20회로도 구분하지 못할 만큼 효과가 작으면 "구분 불가"로 쓰고 편집을 모두 유지하거나 모두 폐기하는 판단만 남는다.
- 편집 E2·E4를 빼면 해당 편집이 겨냥한 목표 필드(gs-008 특이사항 등) 개선을 잃을 수 있다. 원인 편집을 찾더라도 v5는 그 개선과 gs-003 복원을 함께 시험해 확인해야 한다(단계 3).
