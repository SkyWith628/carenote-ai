# Sentinel LLM 보조 단계 설계 (설계만, API 호출 없음)

날짜 2026-10-27. 대상: 규칙이 구조적으로 못 보는 어휘 밖 위험 표현. R-set dev 근거: 규칙 v2 이후에도 어휘 밖 양성 **0/4**(`docs/sentinel-rset-design.md`). 규칙 일반화로 어휘 안 표현은 5/5까지 올랐으니(in-sample) 남은 공백은 의미 이해가 필요한 영역이다.

## 1. 원칙
1. **LLM은 제안만 한다. 판정은 코드가 한다.** LLM 출력은 코드 검증을 통과한 것만 신호가 된다.
2. flag를 **올리기만** 한다(규칙과 같음). LLM이 "위험 아님"이라고 해도 규칙 신호를 내리지 않는다.
3. 모든 신호는 transcript의 **원문 인용**을 가진다. 인용이 없거나 transcript에 없으면 버린다.
4. 실패는 조용하지 않다. LLM 호출 실패는 "신호 없음"이 아니라 "LLM 보조 미실행"으로 기록한다.
5. 진단하지 않는다. 출력 문구는 "확인 필요 위험 신호 후보 + 인용"까지다.

## 2. 위치와 형태
```
transcript ─┬→ Extractor ───────────────→ 필드 ─┐
            ├→ Sentinel 규칙(v2) ─→ signals ─────┤→ Consensus(max) → special_notes flag
            └→ Sentinel LLM(별도 호출) ─→ 검증 ─→ signals(source=llm) ─┘
```
- **별도 호출**(Extractor와 분리). 이유: 추출기와 실패가 상관되지 않고, 단독 평가가 가능하며, 한 호출이 한 가지 일(위험 후보 찾기)만 하게 된다. 단점은 호출 1회 추가인데 비용은 §6처럼 미미하다.
- 접점: `FlaggingExtractor(inner, rules, assist=None)`. `assist`를 주지 않으면 지금과 같다. Consensus 우선순위는 그대로(확인 필요 > risk > ok).
- 겹침 처리: 같은 문장에서 규칙과 LLM이 같은 분류를 내면 하나로 합치고 `source="rule+llm"`. LLM만 낸 신호는 `source="llm"`으로 UI에 "LLM 제안, 사람이 인용 확인" 표시.

## 3. 출력 계약 (구조화 출력)
```json
{"signals": [
  {"category": "흉부·호흡|신경·의식|식사·수분|신체 변화|낙상 후|정황",
   "quote": "transcript에서 한 글자도 바꾸지 않고 복사한 구간",
   "subject": "client|other|unclear",
   "timing": "current|past|hypothetical",
   "negated": false}
]}
```
- 위험 신호가 없으면 `signals: []`이 기본이다. 프롬프트가 "없으면 비워라"를 명시한다.
- 분류 enum은 정책 표 6개와 같다. 확장하지 않는다.

## 4. 근거 인용 검증 (코드, 결정적, 단위 테스트 가능)
`verify_signals(transcript, raw, rules) -> (accepted, rejected_with_reason)`. 순서대로 하나라도 걸리면 버리고 사유를 남긴다.
| 검사 | 규칙 | 막는 것 |
|---|---|---|
| V1 부분 문자열 | 공백 연속을 하나로 줄인 transcript 안에 `quote`가 그대로 있어야 한다 (NFC 정규화 후 비교) | 지어낸 인용, 의역 |
| V2 길이·범위 | 4~120자, 문장 경계 2개 이하 | 통째 복사, 빈 인용 |
| V3 분류 | enum 안 | 형식 오류 |
| V4 속성 | `subject ∈ {client, unclear}`, `timing = current`, `negated = false` | 제3자·과거·가정·부정 |
| V5 결정적 가드 대조 | 인용 위치에 규칙의 부정·조건·제3자·과거 가드를 적용해 걸리면 버린다 (LLM이 current/client라 해도) | 모델의 속성 오판 |
| V6 상한·중복 | 한 transcript에 최대 5개, 같은 인용 중복 제거 | 폭주 |
- **V1~V6가 증명하는 것**: 인용이 실재하고, 형식과 속성이 정책을 어기지 않으며, 규칙의 가드와 모순되지 않는다.
- **증명하지 못하는 것**: 인용이 그 분류의 위험을 뜻한다는 의미. 그래서 UI는 인용 원문을 그대로 보여주고 사람이 판단하게 하며, 평가에서는 사람 확인 표본(§7)으로 이 간격을 잰다.
- V5는 LLM 제안만 낮출 수 있고 규칙 신호는 건드리지 않는다.
- 프롬프트 인젝션: transcript는 데이터로 취급한다(시스템 프롬프트 명시). 주입으로 "위험 없음"을 출력시켜도 규칙 신호는 남는다. 주입으로 가짜 신호를 만들려 해도 V1 때문에 transcript에 이미 있는 구간이어야 하며, 오경보 쪽 오류라 안전한 방향이다.

## 5. 프롬프트 설계
- 구성: 역할(보고 우선순위용 후보 찾기, 진단 금지) · 6분류 정의(정책 표의 의미 설명, **규칙 어휘 목록을 주지 않는다**: 목록을 주면 정규식과 같은 곳만 본다) · 제외 기준(만성 통증, 조언·가정, 제3자, 과거, 부정, 비유, 어르신이 아닌 호칭 모호는 `unclear`) · 출력 규칙(원문 복사, 없으면 빈 배열).
- 예시는 **합성하고 짧게**, R-set·골든셋 문장과 겹치지 않게 한다. 겹침은 단위 테스트가 막는다(§8의 n-gram 검사).
- 호칭 모호("할아버지·할머니")는 `subject: unclear`로 내고 신호로 인정한다(놓침이 오탐보다 해롭다는 규칙 v2 결정과 같다).
- 버전을 `SENTINEL_LLM_PROMPT_VERSION`으로 두고 본문을 sha256으로 고정하는 테스트를 둔다(추출기 v1~v4와 같은 방식).
- 모델: **Haiku 5.5 기본**, 기준(§7)을 못 넘기면 Sonnet 5.5. 효과 수준 low, 최대 출력 토큰은 600.

## 6. 비용 추정 (API 호출 0, 단가 기준일 2026-10-26)
호출당 입력 2,240~2,912토큰(프롬프트 약 2,500자 + transcript 약 260자 + 스키마 400, 글자/1.5), 출력 150~1,500토큰.
| 실행 | 호출 | Haiku 5.5 | Sonnet 5.5 |
|---|---|---|---|
| 호출 1회 | 1 | $0.0003 ~ $0.0010 | $0.0060 ~ $0.0208 |
| dev R-set 20 | 20 | $0.006 ~ $0.021 | $0.120 ~ $0.416 |
| dev 골든 30 (오경보 점검) | 30 | $0.009 ~ $0.031 | $0.179 ~ $0.625 |
| dev 50 합계 | 50 | **$0.015 ~ $0.052** | $0.299 ~ $1.041 |
| dev 50 × 5회 반복(변동 측정) | 250 | $0.075 ~ $0.260 | $1.495 ~ $5.206 |
| test R-set 20 (1회) | 20 | $0.006 ~ $0.021 | $0.120 ~ $0.416 |
| 운영 1,000건 | 1,000 | $0.30 ~ $1.04 | $5.98 ~ $20.82 |
- 승인 게이트는 기존과 같다(추정 최대 이상). Haiku 한 번 돌리는 데 약 $0.06이면 충분하다.
- 보정 근거: Haiku v4 추출 30건이 $0.023(건당 $0.0008)이었다. 이 호출은 출력이 더 짧아 위 하한 근처로 예상한다.
- 호출이 추정보다 비싸지는 경로는 추론 토큰(효과 수준 low로 억제)과 재시도다.

## 7. 평가 계획 (사전 등록)
**데이터**: dev R-set 20건(규칙은 이미 이 케이스에 맞춘 in-sample이지만 **LLM 프롬프트는 이 케이스를 본 적이 없다**) + 기존 dev 골든 30건(특이사항 음성 오경보 점검). test R-set은 동결 후 한 번.
**예측** (틀려도 지우지 않는다):
| 항목 | Haiku 예측 | Sonnet 예측 |
|---|---|---|
| 어휘 밖 양성 4건(K02·K06·K10·K14) | ≥ 3/4 | 4/4 (K10 요일 기간이 가장 어렵다) |
| 정황 K19 | 별도 보고(정답 미확정) | 별도 |
| 음성 오경보(R-set 10 중 gray 제외 8) | ≤ 1 | ≤ 1 |
| 골든 dev 음성(특이사항 ok 8건 + 값 없음 19건) | ≤ 2 | ≤ 1 (낙상 직전·측정 누락이 후보) |
| K26 "할아버지" | 발동(`unclear`) | 발동 |
| 인용 V1 실패율 | < 5% | < 2% |
**채택 판정**:
- Haiku가 어휘 밖 양성 recall ≥ 75%(3/4 이상)이고 gray 제외 음성 오경보 ≤ 2건이면 Haiku 채택.
- 못 넘으면 Sonnet으로 같은 평가. Sonnet도 못 넘으면 채택하지 않고 규칙 단독으로 둔다.
- 채택 전후 이득은 "규칙 ∪ LLM" 대 "규칙 단독"으로 보고한다.
**절차**: dev에서 프롬프트 수정은 최대 2회, 매번 사유를 남긴다 → 프롬프트 sha256을 `sentinel-llm-v1` 태그로 동결 → test R-set 20건 1회(규칙 v2 태그도 동결 필요). 반복 3회로 σ_run도 잰다(Haiku 약 $0.05~0.16).
**사람 확인**: LLM만 낸 신호 전부와 gray 4건을 사람이 본다("인용이 그 위험을 뜻하는가"). 모델 라벨러만으로는 부족하다(같은 Claude 계열).
**지표**: 어휘 밖 양성 recall + Wilson 구간, 음성 오경보, V1~V6 거절 사유별 건수, LLM 단독 신호 수(검수 부담), 호출 실패율.

## 8. 구현 순서 (승인 후)
| 순서 | 작업 | API |
|---|---|---|
| 1 | `verify_signals`(V1~V6)와 단위 테스트 30개 이상 (지어낸 인용, 공백 차이, 길이, 속성, 가드 대조, 중복, 상한) | 없음 |
| 2 | `sentinel_llm.py`: 프롬프트·스키마·캐시·CostGuard·실패 시 `llm_unavailable`, fake client 테스트(정상, 실패, 파싱 오류, 거절) | 없음 |
| 3 | 프롬프트 버전 sha256 고정 테스트, 프롬프트와 R-set·골든 transcript의 n-gram 겹침 검사 | 없음 |
| 4 | Consensus 연결(`assist` 선택 인자), 기본 동작 불변 테스트 | 없음 |
| 5 | CLI `--sentinel-llm {haiku,sonnet}`: dev 분할만 허용, `--dry-run`, `--approve-cost` | 없음 |
| 6 | dev 50건 Haiku 실행(약 $0.02~0.05 → 승인 $0.06) 후 §7 판정 | 있음 |
| 7 | 필요 시 Sonnet, 반복, 동결 태그, test R-set 1회 | 있음 |

## 9. 위험과 한계
- **같은 계열 문제**: R-set transcript는 Opus가 쓰고 라벨러도 Claude다. 보조 모델도 Claude라 맹점이 겹칠 수 있다. 어휘 밖 recall이 높게 나와도 사람이 쓴 문장에서의 값은 모른다. 사용자가 직접 쓴 transcript 몇 건(R-set 설계의 8건 제안)이 가장 값진 점검이다.
- **표본**: 어휘 밖 양성 4건(+test 5건)이라 구간이 매우 넓다(3/4의 하한 약 30%).
- **경보 피로**: LLM이 규칙보다 넓게 잡는다. 오경보율과 LLM 단독 신호 수를 recall과 함께 보고하고, 기준은 사전 등록으로 고정한다.
- **비결정성**: 같은 입력도 달라질 수 있다. 캐시로 재현하고 반복으로 변동을 잰다.
- **개인정보**: 실제 운영에서는 방문 발화가 API로 나간다. 추출기와 같은 경로이며 별도 동의·마스킹 정책이 필요하다(범위 밖, 운영 전 확인).
- **임상 타당성**: 6분류는 여전히 임시 목록이다. 정황은 전문가 확인 전이라 자동 알림에 연결하지 않는다.
