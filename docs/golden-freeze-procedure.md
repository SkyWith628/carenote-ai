## 2. 동결 전제 조건 (모두 충족해야 `golden-v2-frozen`)

| # | 조건 | 확인 방법 | 상태 |
|---|---|---|---|

## 3. 전문가 검토 일정과 대체 규칙
1. 요청서 `docs/expert-review-R3-G1.md`를 검토자 후보에게 보낸다. 검토자 구하기와 발송은 사용자가 한다(외부 발송이라 내가 하지 않는다).
2. 일정 제안(blueprint 3주차 게이트 11/12 전에 test 실측이 가능하도록): 발송 10/30, 회신 기한 11/9.
3. **기한까지 회신이 없으면 잠정 동결**: R3·G1에 `review_required=true`를 유지한 채 동결하고, 최종 보고에서 이 두 건을 제외한 지표를 헤드라인으로 쓰고 포함 지표는 따로 낸다. 이후 회신이 와서 정답이 바뀌면 7장의 개정 절차(v2.1)를 따른다.
4. 검토 결과로 케이스를 교체하는 경우에도 test 실행 전에만 한다.

## 4. 사람 독립 라벨링 (F2)
목적: "정답이 읽는 사람마다 같다"는 증거. 모델 라벨러는 이를 대체하지 못한다(같은 Claude 계열, 정책을 읽고 라벨).

- **표본(미리 고정)**: 직접 쓰지 않은 test 후보 23건(`author=llm`, `split=test`)에서 시드 `20261026`으로 무작위 10건 추출 → **C3, C5, D2, D4, G1, G3, L2, L3, N2, R3**. 이 목록은 라벨링 결과를 보기 전에 정한 것이라 일치율이 낮아도 표본을 다시 뽑지 않는다.
- 직접 작성 10건은 사용자 본인이 쓴 글이라 블라인드가 성립하지 않아 표본에서 뺐다.
- G1·R3는 사용자가 라벨해도 전문가 검토를 대체하지 않는다(표본에는 포함, 별도 검토).
- 방법: `python -m carenote.generation --render-review docs/reports/v2-blind4.md --blind --spec C3 --spec C5 …`(10개)로 시트와 폼을 만들고 사용자가 정답 없이 라벨. 비교는 `--compare-blind`. 이 단계는 API를 쓰지 않는다.
- 판정: 값 일치율 ≥ 95%(10건 × 8필드 = 80필드 중 76 이상). 미달이면 (a) 불일치를 원인별로 분류, (b) 정책 표 보완, (c) 해당 프로브를 같은 스펙으로 재생성하거나 케이스 교체, (d) **새 표본으로 재측정**. 사람이 합의하지 못하는 케이스는 어려운 케이스가 아니라 나쁜 케이스라 버린다.
- 한계 기록: 라벨러가 정책 작성자와 같은 1인이다. 독립 라벨러가 없다는 점을 동결 기록에 적는다.

## 5. 동결 실행 (F1~F7 충족 후, 이 순서)
1. 작업 트리를 깨끗하게 하고 게이트 3종 통과.
2. 매니페스트 생성: 다음 파일의 sha256, 건수, 날짜, git 커밋을 `data/golden/FROZEN.json`에 기록.
   - `v1.jsonl`, `v2_dev.jsonl`, `v2_test.jsonl`
   - `specs/probe_*.json`(10개), `human/transcripts.json`, `human/evidence.json`
   - `docs/label-policy.md`
   - 후보 JSON 30개의 합본 해시(전수 해시 목록)
3. 매니페스트 검증 테스트 `tests/test_frozen.py` 추가: 파일 해시가 매니페스트와 다르면 실패 → 라벨이 조용히 바뀌는 것을 막는다. 의도적 개정은 7장 절차로 매니페스트도 갱신해야 통과.
4. `docs/decisions.md`에 기록: 날짜, 파일별 sha256, 건수(dev 30/test 30), F1~F7 확인 결과, 잠정 동결 여부(R3·G1), 한계(생성기=평가기 계열, 단일 라벨러, 사후 수정 이력), test 실행 0회.
5. 커밋 후 주석 태그: `git tag -a golden-v2-frozen -m "..."`.
6. 동결 직후 dev 4구성 기준선은 이미 `docs/reports/`에 있다. test 실행은 6장 규칙으로만.

### 구현이 필요한 것 (아직 없음)
- `python -m carenote.evaluation.freeze --write | --check`: 위 2·3번을 자동화하는 작은 도구(순수 로컬, API 없음)와 `tests/test_frozen.py`. 동결 시점에 같이 만든다.

## 6. 동결 후 규칙
- **test**: `--final-report` 없이는 LLM 실행 불가. 최종 ablation 1회만 실행하고 횟수·구성·비용을 결정 로그에 기록. 프롬프트·룰은 test 오류를 보고 고치지 않는다. 고치면 그 test는 dev가 되고 새 test를 만든다.
- **dev**: 프롬프트·룰 개선의 대상. 라벨을 고쳐야 할 때는 7장.
- 모든 보고는 `split`, 프롬프트 버전, 모델, effort를 명시하고 구간(95%)과 짝지은 비교를 함께 낸다. 구간이 0을 포함하면 우열을 주장하지 않는다.

## 7. 개정 절차 (동결 후 라벨 수정)
1. 수정 사유와 근거를 쓰고, 어느 보고서·지표에 영향이 있는지 **먼저 계산**(캐시 재채점, 비용 0).
2. 수정 전후 점수를 결정 로그에 "결과 확인 후 수정"으로 기록. 수정이 모델 출력 쪽으로 움직였는지 명시.
3. 매니페스트 버전을 올려(v2.1, 개정 이력 필드) 갱신하고 새 태그(`golden-v2.1`)를 만든다. 이전 태그는 남긴다.
4. test 점수를 본 뒤의 수정이면 그 사실을 보고서에 표시한다.

### 지금까지의 사후 수정 이력 (모두 결정 로그 참조)
gs-015 맥박 70→72(칠십이), gs-016 특이사항 재라벨, gs-008 특이사항(측정 누락), v2 H6·N3 특이사항, gs-002 특이사항(확인 누락), gs-042(L2) 특이사항(맥박 누락), C2 gray 해제, H1 정답 시각 10:00→09:00(라벨링 전). 이들은 대부분 dev 실측 결과를 본 뒤의 정책 확정에서 나왔다. 따라서 **dev는 라벨이 모델 출력과 상호작용한 이력이 있고 test는 없다**는 비대칭이 있다. 이것이 test를 마지막 1회로만 쓰는 이유다.

## 8. 동결이 보장하지 않는 것
- 라벨의 임상적 타당성(특이사항 risk 기준, 낙상 7일은 임시 관례).
- 생성기(Claude Opus)와 평가 대상(Claude Sonnet/Haiku)이 같은 계열이라는 순환성. 직접 작성 10건과 전문가 검토가 줄이는 장치일 뿐이다.
- 표본 크기: test 30건이면 F1 구간이 ±2~3%p로 넓다. 1~2%p 차이는 구분되지 않을 수 있다.
