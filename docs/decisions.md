- 근거 기록: `.court/20261022-144415/VERDICT.md`

## 2026-10-23 — 골든셋 스키마 확정 (방문기록 1종)
- 결정: 케이스는 합성 transcript + **전 필드(8개) 정답**을 항상 나열한다. 값 없음은 `source=missing`으로 명시한다.
- 필드: visit_start, blood_pressure, pulse, meal_intake, medication_taken, fall_event, mood, special_notes. 위험 필드는 혈압·맥박·복약·낙상.
- 규칙: 위험 필드가 missing이면 정답 flag는 `needs_confirm`. 화자가 번복한 수치는 `value=None` + `candidates` 2개 이상 + `needs_confirm` (임의 선택은 오답, 되묻기가 정답).
- 근거: evidence는 transcript의 부분 문자열이어야 한다. 개인정보 패턴(주민번호·휴대전화)이 있으면 로드 단계에서 거부한다.
- 미정: 필드 목록은 열린 결정 3번(문서 타입·필수 항목)의 잠정안이다. 대회 서식이 나오면 조정한다.

## 2026-10-23 — Eval Runner 지표 정의
- 지표 6개(F1, 근거 없는 값, 환각, 수치 오류, 위험 recall, 확인 recall)와 분모 규칙은 `docs/eval-runner.md`가 원본이다.

- 기준선: oracle(만점), null(하한 0)로 평가기 자체를 검증한다. ablation 표의 "단일 LLM" 행은 2주차 Extractor 완성 후 채운다.

## 2026-10-23 — Extractor 설계 (2주차)
- B0(단일 LLM)와 B1(+근거 강제) 두 변형으로 ablation 첫 두 행을 측정한다. 상세는 `docs/extractor-design.md`.
- flag는 LLM이 내지 않고 코드(Flagger)가 계산한다. 3주차 Rule Engine이 대체한다.
- `special_notes`는 v0에서 값 유무로 채점한다. 정확 일치는 불가능하다.
- 모델은 설정값, 기본 `claude-sonnet-5-5` (사용자 결정). Opus 5.5(상한)·Haiku 5.5(하한)는 같은 골든셋으로 비교 행을 추가한다.

## 2026-10-23 — Flagger (임시 규칙)
- flag는 코드가 계산: 위험 필드 누락·후보 2개 이상·불가능한 수치 → 확인 필요, 미복용·중복 복용 의심·낙상 있음 → risk.
- 수치 범위(수축기 70~260, 이완기 30~160, 맥박 30~220)는 임상 기준이 아니라 STT 오인식 탐지용이다. 고혈압 risk 임계값은 Rule Engine에서 확정한다.
- `FlaggingExtractor`는 빠진 키를 missing으로 채워 위험 필드가 조용히 ok가 되는 것을 막는다.
- 정답 값 기준 상한: 위험 recall 60%, 확인 recall 85%. 나머지는 Rule Engine·Sentinel·Verifier의 몫이다 (`docs/extractor-design.md` 11장).

## 2026-10-23 — LLM 실측은 비용 승인 게이트를 통과해야 실행
- `--approve-cost USD` 없이는 LLM 실행을 거부하고, 추정 최대 비용이 승인액을 넘어도 거부한다. 실행 중 누적 비용이 승인액에 도달하면 중단하며 끝낸 결과는 캐시에 남는다.
- dry-run 추정(Sonnet 5.5, 20건, 캐시 없음): 약 $0.18~$0.87 (글자 수 기반, 출력은 추론량 때문에 범위가 넓다). Opus 5.5는 약 $0.35~$1.75, Haiku 5.5는 약 $0.01~$0.04.

## 2026-10-23 — 첫 실측(B1, Sonnet 5.5, 20건)과 채점 규칙 보완
- 결과(채점 규칙 보완 후, 캐시 재채점): F1 96.0%, 근거 없는 값 0/112, 환각 1/49, 수치 오류 3/29, 위험 recall 60%(=Flagger 상한), 확인 recall 95%. 비용 약 $0.17, 건당 약 4초.
- **결과를 본 뒤의 변경 기록**: `special_notes` 값 유무 채점은 설계 문서 7장(실측 전)에서 정했으나 러너에 빠져 있었다. 실측 후 구현했다. 이 규칙은 모델이 아닌 필드 성격(자유 문장) 때문이며 모든 extractor에 동일하게 적용된다. 적용 전 F1은 95.1%였다.

## 2026-10-23 — 골든셋 라벨 수정 (결과 확인 후 수정)
- **이 수정은 첫 실측 결과를 본 뒤에 했다.** gs-015 맥박 정답을 `70`에서 `72`로 고쳤다. transcript는 바뀌지 않았으므로 캐시는 그대로 유효하다.
- 근거: 발화 "맥박은 칠십이고"는 문자 그대로 72이며, 작성자(1인)의 라벨 오류였다. 모델이 72로 읽은 것이 옳았다. 모델 출력과 일치시키려는 목적이 아니라 문장 해석이 근거다.
- 영향: B1 + Flagger 기준 전체 F1 96.0% → 96.9%, stt_error F1 82.1% → 87.2%, 수치 오류 3/29 → 2/29. **이 한 건이 점수를 올렸으므로, B1 첫 실측의 수정 전 값(F1 96.0%)을 함께 기록해 둔다.** 이후 비교(B0, 다른 모델)는 수정 후 골든셋으로 한다.
- 보류: gs-010 맥박 "칠십이었나 팔십이었나"는 70/80과 72/82 둘 다로 읽히는 진짜 모호함이다. 현재 러너가 `candidates` 값을 채점하지 않아 점수에 영향이 없다. 후보 값 채점을 추가할 때 transcript를 "칠십 정도였나 팔십 정도였나"로 바꿔 의도를 살린다(API 1회, 약 $0.01).
- 교훈: 구체적 수치를 의도했다면 골든셋에 한글 수사 대신 명확한 표현을 쓴다("칠십이"는 70+이/72 모호).
