# 케어노트AI 설계도 (Blueprint v1.1)

> v1.1 2026-10-22 · **개인 프로젝트(1인)** · 대회 예상 12월 중순(약 8주) · 공고 미공개
> v1.1 변경: /court 재판(유죄 5:1)의 무죄 조건 반영 — 피치를 "A + 라이브 데모"로 축소, B·C는 stretch(택1), 얇은 E2E 데모를 2주차로 당김, "최소 수상 라인" 표현 삭제, 비용·지연 추정 추가. 기록: `.court/20261022-144415/`
> 이전 설계는 `../_archive/케어노트AI-v1`로 보관. 이 문서는 아이디어에서 새로 쓴 것이다.

## 1. 한 줄과 문제

**한 줄**: 요양보호사가 말로 남긴 방문 기록을, 근거가 붙은 항목별 초안으로 바꾸고, 에이전트가 교차검증한 뒤 사회복지사가 승인한다.

| 사용자 | 아픈 곳 | 케어노트가 하는 일 |
|---|---|---|
| 요양보호사 (현장, 폰, 손이 바쁨) | 방문 후 기록 작성 부담, 누락 | 말하면 항목이 채워지고 부족한 것만 되묻는다 |
| 사회복지사 (검수) | 문장이 어디서 나왔는지 모름, 위험 신호를 놓침 | 항목마다 "원문 보기", 확인 필요·위험 우선 정렬 |
| 센터 (관리) | 기록 품질 편차, 개인정보 부담 | 감사 로그, 온디바이스 마스킹, 센터별 서식 적응 |

## 2. 설계 원칙

1. LLM은 **추출만** 한다. 판정은 코드 룰, 확정은 사람.
2. **근거 없는 값은 없다.** 모든 필드에 evidence 구간. 없으면 `missing`.
3. 불확실하면 **조용히 채우지 않고 드러낸다** (`확인 필요`).
4. 원본은 지우지 않고 **revision으로 쌓는다.** AI안↔사람 최종안의 diff가 품질 신호다.
5. 혁신은 **수치로 증명되는 것만** 넣는다. 모든 단계에 ablation.

## 3. 피치와 혁신 (1인 기준으로 재정렬)

**피치 = A + 라이브 데모.** 말하면 근거 링크가 걸린 항목별 초안이 나오고, 에이전트가 교차검증한 결과가 수치로 증명된다.

| 구분 | 혁신 | 겨냥하는 문제 | 증명 방법 | 지위 |
|---|---|---|---|---|
| **A** | **교차검증 멀티에이전트 + 재청취(Re-listen)** | 환각, STT 오류의 LLM 전파 | 단일→+Verifier→+Re-listener ablation (환각률·수치 오류율) | **핵심 (반드시)** |
| B | 자가개선 하네스 (검수 편집 → 프롬프트·룰·메모리 개선) | 센터별 서식·말투 차이, 정답 라벨 부재 | 학습 전/후 편집 거리 감소 | stretch (택1) |
| C | 온디바이스 프라이버시 (STT+PII 마스킹을 기기에서) | 음성 외부 유출 | 서버 도달 데이터 검증, WER 비교 | stretch (택1) |

- 1인이므로 B·C는 **둘 중 하나만**, 6주차 말에 A·데모 상태를 보고 선택한다. 못 하면 설계 + 부분 시연으로 발표한다.
- 보강(D 추세 경보, E 목업 폼 자동채움, F MCP/A2A)은 범위에서 제외한다. 시간이 남아도 A의 품질과 데모 안정성에 쓴다.

## 4. 시스템 구조

```
[기기: Next.js PWA]
  녹음 → (C) 온디바이스 STT + PII 마스킹
        └─ 마스킹 transcript ──────────────┐   (위험 구간 오디오는 동의 시에만 업로드)
                                          ▼
[FastAPI] ── Orchestrator (LangGraph: 병렬 팬아웃 / interrupt HITL / 체크포인트)
   │   ┌────────────┬──────────────┬─────────────┐
   │ Extractor   Rule Engine    Sentinel      (병렬)
   │   │         (코드, YAML)   (위험·상태변화)
   │   └→ Verifier(타 모델) → Re-listener(오디오 네이티브, 위험 필드만)
   │                          → Consensus(코드) ─ 통과 → Review
   │                                            └ 부족 → Clarifier → 답변 → 해당 필드 재추출
   ▼
[Postgres] drafts · draft_revisions · audit_log · timeline · harness_versions
[Eval Runner] 골든셋 ablation · 하네스 후보 Probe
[Offline 야간] (B) 개선 루프: diff → 후보 → 회귀 → 관리자 승인 → 배포
```

### 4.1 에이전트 역할

| 에이전트 | 입력 | 출력 | 비고 |
|---|---|---|---|
| Extractor | transcript, 문서 스키마 | 필드별 `{value, evidence[], source}` | 구조화 출력(JSON Schema) 강제 |
| Verifier | 필드 + 근거 구간 | `supported / unsupported / ambiguous` | Extractor와 **다른 모델 계열** |
| Re-listener | 위험 필드의 오디오 구간 | 값 재확인 | 수치·복약·낙상만. 동의 시 구간 업로드 |
| Sentinel | 전체 초안 + 최근 타임라인 | 위험 신호·우선순위 | 룰 우선, LLM은 보조 |
| Clarifier | 실패한 룰 | 되묻기 질문 | 템플릿 우선, LLM은 문장 다듬기만 |
| Consensus | 위 결과들 | 최종 플래그 | **코드**. 불일치 → `확인 필요` |

위험 필드(수치·복약·낙상·상태변화)에만 비싼 검증을 건다. 비용·지연은 이 필터로 통제한다.

### 4.2 필드 계약

```json
{
  "key": "blood_pressure",
  "value": "130/80",
  "source": "stated",              // stated | inferred | missing
  "evidence": [{"start_ms": 8200, "end_ms": 10400, "text": "혈압은 130에 80이고요"}],
  "checks": {"verifier": "supported", "relisten": "agree", "rule": "in_range"},
  "flag": "ok"                     // ok | needs_confirm | risk
}
```

## 5. 데이터 모델 (MVP)

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| organizations / users | org_id, role(caregiver·social_worker·admin) | RBAC, 모든 테이블에 org_id + RLS |

| audit_log | actor, action, target, at | 수정 불가 |
| timeline | recipient_id, visit_id, metrics JSONB | D 추세 경보 기반 |
| harness_versions | version, prompts, rules, memory, eval_report, approved_by | B 배포 단위, 롤백 가능 |

## 6. 개인정보·보안

- 건강정보는 민감정보다. 수급자를 **녹음 전에 선택**하므로 프롬프트에는 이름을 넣지 않고(`수급자A`, 연령대·등급만), 잔여 이름은 사전+정규식으로 치환한다.
- 오디오는 기본적으로 기기를 떠나지 않는다 (C). 재청취용 구간 업로드는 동의 후 확정 즉시 삭제.
- transcript는 비신뢰 입력(프롬프트 인젝션). 출력은 스키마로만 받고 에이전트에 부작용 있는 도구 권한을 주지 않는다.
- 로그에 본문·식별정보 금지. JWT 단기+갱신, RLS, 암호화 키는 앱 코드와 분리.
- 하네스는 **운영 중 자기 수정 금지.** 회귀 통과 + 관리자 승인 + 버전 롤백.

## 7. 평가 설계 (수상의 핵심)

- **골든셋**: 합성 transcript 60건 목표 — 정상, 누락, 모호한 수치("130에 80"), 방언·말더듬, STT 오인식, 위험 조합, 프롬프트 인젝션 시도.
- **지표**: 필드 F1 · **근거 없는 값 비율(목표 0%)** · 수치 오류율 · 누락 탐지 recall · 위험 탐지 recall · 운영 시 편집 거리·검수 시간.
- **ablation 표** (발표 핵심 슬라이드):

| 구성 | 환각률 | 수치 오류 | 비용/건 | 지연 |
|---|---|---|---|---|
| 단일 LLM | | | | |
| + 근거 강제 | | | | |
| + Verifier | | | | |
| + Re-listener | | | | |
| + 하네스 개선(B) | | | | |

- 오디오 평가셋: 합성 음성(TTS) + 직접 녹음 소량. 실제 수급자 음성은 쓰지 않는다.

## 8. 일정 (1인, 10/22 → 12월 중순, 약 8주)

> 가정: 대회가 12/12~12/19 사이. **7주차를 리허설·버퍼로 잡고 기능은 6주차 말에 동결**한다. 주당 가용 시간은 확인 필요 — 확인 후 각 주 범위를 조정한다.

| 주 | 목표 | 완료 기준 |

| 6 (~12/3) | 골든셋 60건, 비용·지연 표, 데모 다듬기. stretch 택1 최소 버전(B-lite 또는 C PoC) | 기능 동결 |
| 7 (~12/10) | 발표자료, 시연 시나리오, 리허설 3회, 버퍼 | 라이브 시연 무사고 |

- 공고가 나오는 날 제출 형태·배점을 대조하고 6~7주차를 조정한다.

### 8.1 비용·지연 추정 (측정 후 채울 틀)

## 10. 열린 결정 (기록할 것)

1. STT: 서버 STT로 먼저 시작(2주차), 온디바이스는 C를 택할 때만 후보 실측
2. Extractor·Verifier·Re-listener에 쓸 구체 모델 (구현 직전 공식 문서 확인)
3. 대상 문서 타입과 필수 항목 (방문기록 1종으로 시작)
4. 시안 재사용 범위 (`_archive/케어노트AI-v1/design/`)
5. 주당 가용 시간 (1인 일정의 전제)
6. stretch 택1(B-lite vs C) — 6주차 말 결정
7. 개인 참가의 시상·참가 조건 — 이전 아이디어 대회에는 "개인 부문 시상금 없음" 조항이 있었다. 구현 대회 공고에서 확인할 것
