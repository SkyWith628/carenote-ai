# KR-1 완화: Flagger 번복 표현 규칙과 만들어진 숫자 규칙 (설계, 구현 전)

`docs/known-risks.md` KR-1(번복이 풀리지 않은 혈압을 확정 값으로 내는 오류)의 코드 완화책이다. 모델이 못 고치는 약점을 결정적 규칙으로 보완한다. API를 쓰지 않는다. **아직 구현하지 않았다.**

## 1. 원칙
- 규칙은 flag를 **올리기만** 한다(ok → needs_confirm). 값은 건드리지 않는다. 위험 필드의 조용한 오답을 사람 검수로 넘기는 것이 목적이다.
- 입력은 transcript와 모델 출력뿐이다. 판정은 코드.
- 검증은 dev 캐시로만 했다(test는 보지 않음). 규칙은 dev 데이터에서 만들었으므로 **표본 안(in-sample) 결과**다. 일반화는 test 최종 보고에서 처음 확인된다.

## 2. 규칙 R1 — 번복·불확실 의문형 표지 (hedge guard)
- 대상: `blood_pressure`, `pulse`, 모델이 **단일 값**을 낸 경우(후보가 2개 이상이면 이미 needs_confirm).
- 발동: transcript에 수사(아라비아 숫자 또는 한자어 수사 연속)가 있고 바로 뒤에 선택적 `이`와 의문형 어미 `었나·였나·인가·던가·일까·인지`가 붙는 표현이 있을 때. 표현이 속한 문장에서 앞쪽에서 가장 가까운 키워드(`혈압`, `맥박`)의 필드에 적용하고, 키워드가 없으면 두 필드 모두에 적용한다.
  - 정규식 초안: `(?:\d+|[영공일이삼사오육칠팔구십백천]+)\s?이?(?:었나|였나|인가|던가|일까|인지)`
- 동작: flag = `needs_confirm`(이유 코드 `hedge_in_transcript`).
- 비발동(의도): "130에 80, 아니 죄송해요, 140에 90이었어요"처럼 **서술형으로 끝나는 정정**은 의문형 표지가 없어 건드리지 않는다. 이것은 설계 가정이며 dev에는 해당 사례가 없어 검증하지 못했다(아래 6장).

## 3. 규칙 R2 — 만들어진 숫자 (fabrication guard)
- 대상: 같은 필드, 단일 값.
- 발동: 값의 각 숫자(혈압은 수축기·이완기, 맥박은 한 개)가 `extract_numbers(transcript)`(아라비아 숫자와 한자어 수사의 모든 부분 읽기)에 없을 때.
- 동작: flag = `needs_confirm`(이유 코드 `number_not_in_transcript`).
- 알려진 한계: 값이 transcript의 **다른 곳**에 있는 숫자와 우연히 같으면 못 잡는다(예: 이완기를 수축기 근처 숫자에서 가져옴). gs-003의 82는 "팔십이었나"의 `이`를 숫자로 읽은 값이라 `extract_numbers`가 82를 포함하므로 R2가 아니라 R1이 잡는다.

## 4. dev 캐시 검증 (API 호출 0)
범위: dev 30건 × 혈압·맥박 × 캐시에 있는 모든 실행(프롬프트 v1~v4, Haiku·Sonnet, B0·B1, 반복 태그 포함) = **2,360행, 실행 설정 78개**. 스크립트: `docs/reports/20261026-kr1-flagger-prototype.py.txt`(실행하려면 `.py`로 바꿔 `PYTHONPATH=src uv run python`).

| 항목 | 값 |
|---|---|
| 정답이 "해소 안 됨"(후보 두 개)인 행 | 154행 = 후보를 냄 115 + **단일 값 확정 39**(39행 모두 flag ok) |
| R1 발동 | **39행, 전부 위의 단일 값 확정 행.** 정답이 해소된 행에서의 오경보 **0** (발동 케이스는 gs-003 혈압, gs-009 혈압, gs-010 맥박뿐) |
| R2 발동 | **7행, 전부 오답**(gs-053 혈압 `120/90`·`130/90`(정답 140/90) 6행, gs-019 맥박 `72`(정답 60) 1행). 정답 값에서의 오경보 **0** |
| 정답이 needs_confirm인 혈압·맥박 행의 확인 recall | 현재 533/572(93.2%) → R1 적용 후 **572/572(100%)** (표본 안) |
| "조용한 오답"(단일 값 + flag ok + 값이 정답과 다름) | 1,823행 중 **49행** → R1이 39, R2가 7, 합집합 46 → **남는 3행** |
| 남는 3행 | 전부 gs-015 맥박 `70`(정답 72, "칠십이고"의 수사·조사 모호성) |
| 과다 확인(정답 flag ok인데 needs_confirm) | 현재 4행. 두 규칙으로 늘어나는 것 **0** |

### 모델별로 보면 KR-1은 Haiku 문제다
정답이 해소 안 됨인 세 케이스(gs-003, gs-009, gs-010)에서 단일 값을 확정한 비율:

| 모델·변형 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|
| Sonnet B0·B1 | 0/6 | 0/6 | 0/6 | 미측정 |
| Haiku B0 | 0/3 | 0/15 | 2/15 | 4/15 |
| Haiku B1 | 0/3 | 2/15 | 13/35 | 18/35 |

- Sonnet은 단일 실행이라 확정적이지 않지만 18행 모두 후보를 냈다.
- Haiku는 v1·v2에서는 거의 안 틀렸고 v3에서 늘었으며 v4에서 더 늘었다. 합치면 Haiku의 단일 확정 비율이 **v3 15/50(30%) → v4 22/50(44%)**, v4가 더 많을 단측 p = **0.107**(탐색적, 구분 불가이나 방향이 일관). ablation 단계 0(gs-003만, B1 20회)의 p=0.374와 같은 방향의 약한 신호다. **v4 채택의 알려진 비용 후보**로 기록한다. Flagger 규칙이 이 오류를 사람 검수로 돌리므로 영향을 제한한다.

## 5. 검토했으나 채택하지 않은 것
| 안 | 이유 |
|---|---|
| R3 모호한 수사("칠십이고"류)가 있으면 그 필드를 모두 needs_confirm | gs-015 맥박은 단일 값 38행 중 35행이 정답(72)이다. 3건을 잡으려고 35건을 오경보 → 과다 확인 비용이 크다. 정책(사용자 결정: 72)과도 충돌 |
| 값을 None으로 강등(demote) | 값을 바꾸면 F1 채점이 달라진다. 1차 구현은 flag만 올린다. 강등 효과는 별도 실험으로 잰다 |
| 2차 표지(`헷갈`, `기억이 안`, `잘 모르겠`, `가물가물`) | dev에서 이 표지로 확인되는 사례는 gs-009 한 건이고 이미 R1이 잡는다. 검증할 수 없어 보류 |
| R1을 B1 evidence 인용에만 적용 | B0에는 인용이 없고 transcript 전체에서 찾는 쪽이 단순하다 |

## 6. 위험과 검증되지 않은 가정
- **오경보 가능성(dev 밖)**: 해소된 정정 문장이 의문형으로 끝나면("140이었나? 아니 130이었어요") R1이 불필요하게 확인을 요청한다(정답 flag는 ok인데 needs_confirm). 의도한 보수적 동작이지만 비용이 있다. 합성 음성 대조 문장 15~20개를 **단위 테스트로만** 만들어 확인한다(골든셋은 동결이라 추가하지 않는다).
- 의문형 표지가 수치 앞이 아니라 문장 끝에만 오는 경우("백삼십에 팔십, 아니 백사십에 팔십 아니었나 싶기도 하고")는 못 잡는다.
- R2는 `extract_numbers`의 관대한 읽기에 의존한다(숫자를 놓치는 쪽보다 있다고 보는 쪽으로 설계). 그래서 놓칠 수는 있어도 오경보는 적다.
- 표본 안 결과다. 새 번복·불확실 케이스(test의 C3 등)에서 처음 일반화가 확인된다.

## 7. 구현 계획 (승인 후, API 없음)
| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | `flag_field(field, transcript=None)`: transcript가 있을 때만 R1·R2 적용(하위 호환). `FlaggingExtractor`가 transcript를 넘김 | 기존 Flagger 테스트 통과, 새 규칙은 transcript 유무에 따라 동작 |
| 2 | R1 정규식과 필드 연결, R2 값 파싱 | 합성 양성 문장(해소 안 됨)·음성 대조 문장(서술형 정정, 일반 수치, 의문형이 수치와 무관) 단위 테스트 |
| 3 | 러너 지표 추가: **조용한 오답률**(단일 값 + flag ok + 값 오답), **과다 확인률**(정답 ok인데 needs_confirm) | oracle 0, 의도적으로 틀리는 extractor로 값 검증 |
| 4 | dev 캐시 재채점으로 효과 확인(비용 0): v3·v4 Haiku/Sonnet 보고서의 확인 recall, 조용한 오답률, 과다 확인률 | 위 4장 수치가 재현되고 F1은 변하지 않음(flag만 올림) |
| 5 | 동결 영향 점검 | 골든셋 파일 불변(`freeze --check`) |

## 8. 이 설계가 말하지 않는 것
- 규칙이 모델의 값 오류 자체를 고치는 것은 아니다. 틀린 값은 그대로이고 사람에게 확인을 요청할 뿐이다.
- 확인 recall 100%는 표본 안(dev의 세 케이스, gs-014·015 포함) 값이다.
