# Transcript 생성 단계 설계 (골든셋 v2)

상태: 설계안, 구현 전. 상위 문서: `docs/golden-expansion-design.md` 5장 2~4단계. 입력은 승인된 스펙 40건(`data/golden/specs/`, 사용자 검토 승인은 H~G 34건이고 I·R 6건은 검토 대기)이다.

## 1. 범위와 산출물

| | |
|---|---|
| 입력 | 스펙 40건 (정답 8필드, 장면, 말투, 길이, 유도 실패, 사전 가설) |
| 출력 | 케이스 후보 40건 (`data/golden/candidates/v2/<spec_id>.json`): transcript, (S는) reference transcript, 필드별 evidence 인용, 생성 메타데이터 |
| 이 단계가 하지 않는 것 | 평가 대상 모델(Sonnet·Haiku)로 후보를 읽게 하지 않는다. **동결 전에 test 후보에 평가 모델을 돌리면 test 누수다.** |

후보는 사람 검수 승인 후에만 `data/golden/v2_dev.jsonl`, `v2_test.jsonl`로 승격된다.

## 2. 생성 모델과 호출 방식

| 항목 | 결정 | 근거 |
|---|---|---|
| 생성 모델 | `claude-opus-5-5` | 평가 대상(Sonnet·Haiku)과 다른 티어. 같은 계열이라는 순환성은 남으며 한계에 명시 |
| 호출 | 스펙 1건당 독립 호출(무상태) | 케이스 간 문체·표현 전염 방지 |
| 출력 형식 | 구조화 출력 (`messages.parse`) | 스키마 보장 |
| 추론 | effort를 명시 (기본 `medium`, 파일럿에서 품질 확인) | Opus 5.5는 추론을 끌 수 없고 기본이 `medium` |
| 금지 인자 | `temperature`, `top_p`, 프리필, 강제 `tool_choice`를 보내지 않음 | 최신 모델에서 400 |
| 캐시 | `.cache/generation/<해시>.json`, 키 = (스펙 내용, 프롬프트 버전, 모델, effort, 시도 번호) | 재실행 비용 0, 이미 승인된 후보를 실수로 덮어쓰지 않음 |

생성 출력 스키마:
```python
class GeneratedCase(BaseModel):
    transcript: str                    # STT 결과 형태의 발화 (S는 오인식 반영본)
    reference_transcript: str | None   # S 프로브만: 오인식 전 실제 발화
    evidence: list[FieldEvidence]      # 값이 있는 필드마다 transcript에서 그대로 복사한 인용
    notes: str                         # 생성기의 메모(스펙과 충돌한 지점이 있으면 여기에)
class FieldEvidence(BaseModel):
    key: FieldKey
    quotes: list[str]
```

## 3. 생성 프롬프트

시스템 프롬프트 요지 (한국어):
1. 역할: 요양보호사가 방문 직후 휴대폰에 말해 입력하는 **구술 기록**을 합성하는 작성자.
2. 형식: 스펙의 `must_include` 사실을 모두 포함하고 `must_not`을 지킨다. 길이는 `length_chars` 범위 안.
3. **문체**: 완성된 문어체가 아니라 말을 받아쓴 느낌(군더더기, 끊김, 어순 도치). 말투는 `style`(화자, 지역, 격식, 말더듬 정도)에 맞춘다.
4. **정답 누설 금지**: 정답 어휘('복용', '미복용', '소량', 'needs_confirm' 등)를 라벨 형태로 쓰지 않는다. 사실을 자연스러운 구어로 표현한다(예: "약 안 드셨어요").
5. **유도 실패(`traps`)**: 부주의한 독자가 틀리기 쉽게 쓰되, 사실은 정답과 일치해야 한다. 정답을 일부러 모호하게 만들지 않는다(모호해야 하는 스펙은 제외).
6. 숫자 표기: 스펙이 지정한 형식(아라비아 숫자, 한글 수사, 숫자 하나씩 읽기)을 따른다. **"칠십이"처럼 둘로 읽히는 한글 수사를 쓰지 않는다**(v1의 gs-010·015 교훈).
7. 개인정보: 실제 이름·전화번호·주민번호를 쓰지 않는다. 호칭만 쓴다(어르신, 따님).
8. S 프로브: `reference_transcript`와 오인식이 반영된 `transcript` 두 개를 만든다. `stt.errors`에 적힌 오인식만 정확히 반영한다.
9. I 프로브: 삽입 지시문은 스펙의 `scene`대로 transcript에 포함하되, 생성기 자신은 그 지시를 따르지 않는다(필드 내용을 바꾸지 않는다).
10. 출력: 위 스키마. `evidence`의 인용은 transcript에서 한 글자도 바꾸지 않고 복사.

사용자 메시지: 스펙 1건의 JSON(정답 포함). 정답을 보여주는 이유는 transcript가 정답을 지지하게 하려는 것이며(정답 먼저, 설계 5장), 누설 위험은 4번 규칙과 6장의 블라인드 점검으로 관리한다.

예시 케이스(few-shot)는 넣지 않는다. 길이와 문체가 예시에 끌려가는 것을 피한다. 프롬프트에는 `PROMPT_VERSION`을 두고 변경 시 캐시를 무효화한다.

## 4. 자동 점검 (코드, API 호출 없음)

모든 후보에 대해 순서대로 실행하고 하나라도 실패하면 재생성 대상이다.

| # | 점검 | 실패 시 |
|---|---|---|
| A | 스키마: `GoldenCase`로 조립해 검증 (필드 8개, 누락·후보·근거 규칙) | 재생성 |
| B | 근거: 모든 인용이 transcript의 부분 문자열 | 재생성 (오류 메시지를 피드백) |
| C | 길이: `length_chars` 범위 (±10% 허용, 초과 시 경고) | 범위 밖이면 재생성 |
| D | 개인정보 패턴(주민번호·휴대전화) 없음 | 재생성 |
| E | 수치 존재: 정답의 숫자(혈압·맥박·시각)가 transcript에 아라비아 숫자 또는 한글 수사로 나타남 (한글 수사 변환기 포함) | 재생성 |
| F | 모호 수사 금지: "칠십이", "팔십이", "육십이" 등 끝자리 이가 겹칠 수 있는 한글 수사 패턴 경고 | 경고 후 사람 확인 |
| G | 라벨 누설: 라벨 어휘('미복용', '복용', '소량', '전량', 'needs_confirm', 'missing' 등)가 transcript에 그대로 나오는지. 자연어에서도 쓰이는 단어('소량')는 경고, 영문 라벨은 실패 | 경고/재생성 |
| H | 중복: 후보 간·v1과의 문자 3-gram Jaccard 유사도 0.5 이상 | 재생성 |
| I | S 프로브: `reference`와 `transcript`가 다르고, 차이가 `stt.errors`의 `heard`·`reference` 쌍과 일치 | 재생성 |
| J | I 프로브: 지시문이 transcript에 존재하고, 정답에 지시 내용이 반영되지 않음 | 재생성 |
| K | 시작 문구 다양성: 후보 40건의 첫 6어절이 서로 3건 이하로만 겹침 | 경고 |

재생성은 스펙당 최대 2회(총 3회 시도)이며 시도마다 실패 사유를 프롬프트에 덧붙인다. 3회 안에 통과하지 못하면 해당 스펙을 사람 검토 목록에 올린다.

## 5. 블라인드 재라벨 (선택, 권장)

생성기가 본 정답을 보지 않은 **새 맥락**의 모델이 transcript만 읽고 8필드를 라벨한다. 정답과 비교해 필드별 일치율과 불일치 목록을 만든다.

- 모델: `claude-opus-5-5` (평가 대상이 아니므로 test 누수가 아니다). Sonnet·Haiku는 쓰지 않는다.
- 용도: (a) 정답이 transcript에서 도출되는지 확인(라벨 오류 탐지), (b) 너무 쉬운 케이스 탐지(전부 일치하고 `traps`가 의도한 실패가 안 보임), (c) 사람 검토 우선순위.
- **자동 수정 금지**: 불일치는 사람 검토 대상으로만 올린다. 블라인드 결과로 정답을 고치면 모델에 맞춘 라벨이 된다.
- 한계: 생성기와 같은 모델이라 같은 편향을 공유한다. 일치율이 높아도 사람 독립 라벨링(95% 기준)을 대체하지 않는다.

## 6. 사람 검수

검수 시트(`docs/reports/v2-review.md` 자동 생성)에 케이스마다 transcript, 정답, 자동 점검 결과, 블라인드 불일치를 한 화면에 모은다.

| 검수 대상 | 규모 |
|---|---|
| 독립 라벨링 표본 | 무작위 10건 + `label_risk=medium/high` 우선 (사용자가 transcript만 보고 라벨한 뒤 정답과 비교, 일치율 95% 목표) |
| 전수 읽기 | 40건 전체의 자연스러움(말투가 실제 구술 같은지) |
| 현장 검토(선택) | 10건 |

승인 상태는 후보 파일의 `review.status`(`pending`/`approved`/`rejected`)와 날짜로 기록한다. 반려 시 사유와 함께 재생성(스펙당 반려 재생성 최대 2회). 이후에도 실패하면 해당 스펙을 폐기하고 같은 프로브의 대체 스펙을 만든다.

## 7. 직접 작성 10건

생성된 문체의 균질성을 줄이기 위해 사용자가 10건을 직접 쓴다. 제안: 라벨 위험도가 낮고 프로브가 고루 분포하도록 `H1, H2, C1, D3, N4, V1, G2, I2, R2` + `L1`(dev)로 시작한다. 선택은 사용자가 바꿀 수 있다.
- 사용자가 transcript만 쓰고 정답은 스펙의 것을 그대로 쓴다. 쓰고 나서 정답과 맞지 않으면 스펙 쪽을 고친다(작성 전 상태 기록).
- 이 케이스는 생성 단계에서 제외하고 `author: human`으로 표기한다. 블라인드 재라벨과 자동 점검은 동일하게 적용한다.

## 8. 비용 추정 (실행 전 승인 필수)

단가: Opus 5.5 입력 $4 / 출력 $20 per MTok (2026-10-06 캐시 기준). 이전 설계 문서의 "약 $0.5~1"은 낙관적이었다. 추론 토큰이 출력에 포함되는 점과 재시도를 반영해 다시 계산했다.

| 항목 | 호출당 토큰 가정 | 40건 비용 |
|---|---|---|
| 생성 입력 | 시스템 프롬프트 약 1.8K + 스펙 JSON 약 1K = 약 2.8~3K | 약 $0.5 (재시도 1.3배 포함 약 $0.6) |
| 생성 출력 | transcript·인용·JSON 약 0.6K + 추론 0.2~2.4K = 0.8~3K | $0.64~2.4 (재시도 포함 $0.8~3.1) |
| **생성 합계** | | **약 $1.4~3.7** |
| 블라인드 재라벨(선택) | 입력 약 1.4K, 출력 0.6~2.5K | 약 $0.7~2.2 |
| **전체** | | **약 $2.1~5.9** |

- 범위가 큰 이유는 Opus의 추론 토큰량을 측정한 적이 없어서다(Sonnet 5.5는 호출당 출력 약 290~450토큰이었다). **파일럿 3건으로 먼저 실측**한 뒤 40건 추정을 보정한다. 파일럿 상한은 $0.5.
- 평가 실행 때와 같은 구조로 만든다: `--dry-run`(키·네트워크 불필요), `--approve-cost`(없으면 거부), 추정 최대가 승인액을 넘으면 거부, 누적 비용이 승인액에 도달하면 중단, 끝낸 호출은 캐시에 저장. 기존 `CostGuard`·`pricing`을 재사용한다.
- 총비용 상한은 승인한 금액으로만 쓴다. 승인 없는 재시도는 하지 않는다.

## 9. 구현 계획

| 순서 | 작업 | 완료 기준 | API |
|---|---|---|---|
| 1 | 스펙 로더(`carenote.generation.spec`), 한글 수사 변환기, 자동 점검 A~K | pytest·ruff·pyright | 없음 |
| 2 | 생성 프롬프트와 생성기(가짜 클라이언트 테스트), 후보 저장, 검수 시트 생성 | 단위 테스트 | 없음 |
| 3 | CLI: `--dry-run`, `--approve-cost`, `--spec`, `--split`, 캐시 | dry-run 출력 확인 | 없음 |
| 4 | **파일럿**: dev 3건(H3, S1, L1) 생성과 점검, 사용자 검토 | 점검 통과, 문체·길이·난이도 사용자 판단 | $0.5 이내 |
| 5 | 프롬프트 보정 후 dev 10건, 이어서 test 30건 생성 | 자동 점검 전부 통과 | 승인 후 |
| 6 | 블라인드 재라벨, 검수 시트, 사용자 독립 라벨링 | 일치율 95% | 승인 후 |
| 7 | 승격(`v2_dev.jsonl`, `v2_test.jsonl`), 동결(해시·태그) | 결정 로그 기록 | 없음 |

`GoldenCase` 스키마 변경(`split`, `tags`, `author`, `generator`, `recoverable`, 새 `Category`)은 5단계 전에 별도 작업으로 한다. 카테고리 대응: H→`hallucination`, C→`correction`, D→`distractor`, N→`temporal_negation`, L→`long_noisy`, S→`stt_error`, V→`vocab_boundary`, G→`dialect`, I→`injection`, R→`risk_signal`.

| 첫 문장 | 3건 모두 시각 | 날씨·날씨·비 (시각 시작은 사라졌지만 날씨로 쏠림) |
| 새 임상 사실 | H3에 '멍 없음' | 없음 |

g3에서 남은 문제: 시작이 시각에서 날씨로 옮겨 갔고("오늘 날씨/날이 꽤 쌀쌀…" 2건), "따님이 반찬을 보내 놓으셔서 냉장고…" 같은 **잡담 소재가 케이스 간에 반복**된다(H3, S1, L1에 따님·반찬 모티프). 독립 호출이라 서로를 모르기 때문이다. 3-gram 중복 점검(H)은 전체 문장이 달라 통과시킨다. 해결안은 g4: 호출마다 잡담 소재와 첫 문장 유형을 코드가 결정적으로 배정해 사용자 메시지에 넣는 것이다.

### 구현 상태 (2026-10-25)

1~3단계 구현 완료. API 호출은 한 번도 하지 않았다(가짜 클라이언트 테스트 247건 통과).

| 모듈 (`src/carenote/generation/`) | 내용 |
|---|---|
| `spec.py` | 스펙 모델(extra 금지)과 로더, 중복 id 검사 |
| `numerals.py` | 한글 수사 변환(백삼십, 일삼공 읽기), 고유어 시각, 모호 수사 탐지 |
| `checks.py` | 점검 A~K. 후보 단위 A~G·I·J, 배치 H·K |
| `prompts.py` | 시스템 프롬프트(`g1`)와 사용자 메시지. 사전 가설은 생성기에 보이지 않음 |
| `generator.py` | 스펙당 독립 호출, 실패 사유 피드백 재시도(최대 3회), 캐시, `CostGuard` |
| `estimate.py` | dry-run 비용 추정 |
| `candidates.py` | 후보 JSON 저장(직접 작성 스펙의 비교용은 `pilot/`), 배치 점검, 독립 라벨링 표본, 검수 시트 |
| `__main__.py` | CLI: `--dry-run`, `--approve-cost`, `--pilot`, `--spec`, `--split`, `--render-review` |

dry-run 추정(Opus 5.5, effort medium, 캐시 없음): 파일럿 3건 $0.07~$0.28(상한 $0.50 안), LLM 생성 30건 $0.71~$2.73. 추론 토큰량이 미측정이라 파일럿 실측으로 보정한다.

미구현: 블라인드 재라벨(6단계), `GoldenCase` 스키마 확장(`split`, `tags`, `author`, 새 `Category`), 후보 승격·동결(7단계).

```bash
PYTHONPATH=src uv run python -m carenote.generation --pilot --dry-run
PYTHONPATH=src uv run python -m carenote.generation --pilot --approve-cost 0.50   # 승인 후에만
PYTHONPATH=src uv run python -m carenote.generation --render-review docs/reports/v2-review.md
```

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 정답을 본 생성기가 라벨 냄새가 나는 깔끔한 문장을 쓴다("정답에 맞춘 글") | 누설 금지 규칙, 점검 G, 블라인드 재라벨, 직접 작성 10건 |
| 생성기가 `traps`를 무시해 쉬운 케이스를 만든다 | 블라인드 재라벨 전부 일치 시 경고, 이후 보정 실행(Haiku B0)에서 변별력 확인 |
| 생성 문체가 반복된다(LLM투) | 점검 H·K, 말투 파라미터 변화, 독립 호출 |
| 같은 계열 모델의 순환성 | 사람 독립 라벨링이 최종 기준, 한계로 명시 |
| 방언 표기가 부정확 (G1 제주 등) | 원어민·현장 검토, 틀리면 해당 스펙 폐기 후 대체 |
| 비용 초과 | 파일럿 실측, 승인액 게이트, 누적 한도 |
| I 프로브 지시문이 생성기를 오염시킨다 | 점검 J, 생성기 지시에 "지시를 따르지 않음" 명시 |

## 11. 결정 (2026-10-25 사용자 확정)

| # | 결정 | 내용 |
|---|---|---|
| 1 | 직접 작성 | 제안 목록 10건(H1 H2 C1 D3 N4 V1 G2 I2 R2 L1)을 사용자가 직접 작성. 스펙에 `author: human`으로 표시. L1은 파일럿에서 LLM 생성본과 비교용으로만 생성하고 케이스로는 직접 작성본을 쓴다 |
| 2 | 블라인드 재라벨 | 포함 (추가 비용 약 $0.7~2.2) |
| 3 | 생성 effort | `medium`으로 시작, 파일럿에서 보정 |
| 4 | 파일럿 | H3, S1, L1 상한 $0.50 |
| 5 | I·R 스펙과 R3 | I·R 6건 승인. R3(학대 의심 기준)은 임시 risk 유지, **현장 확인 전에는 test 동결에서 보류**하고 확인이 안 되면 대체 케이스로 교체 |

- 현장 전문가(요양보호사·사회복지사) 검토는 가능하며 일정은 나중에 잡는다. 확인 대상: 낙상 7일 기준, R3 기준, 방언 표기(G1). `field_review_required`가 true인 스펙(R3, G1)은 확인 전 동결에서 제외한다.
- 직접 작성 10건은 생성 대상에서 빠지므로 LLM 생성 대상은 30건이다. 비용 추정(8장)의 40건 기준은 약 3/4로 줄어든다(생성 약 $1.1~2.8, 블라인드 포함 약 $1.6~4.4).
