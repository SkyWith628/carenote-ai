# 골든셋 확장 설계 (v1 20건 → v2 60건)

상태: 설계안, 구현 전. 근거: `docs/ablation.md` (20건이 포화되어 구성 간 차이가 노이즈).

## 1. 목표와 성공 기준

목표는 **구성(모델, B0/B1, 프롬프트)을 구분할 수 있는 평가 도구**를 만드는 것이다. 점수를 높이는 것이 아니다.

| 기준 | 값 | 확인 방법 |
|---|---|---|
| 규모 | 60건 (기존 20 + 신규 40) | 로더 검증 |
| 변별력 | 신규 40건에서 Haiku B0의 F1이 60~90% | 라벨 동결 후 1회 측정. 어떤 구성이든 98% 이상이면 포화로 판정하고 케이스를 추가 |
| 라벨 신뢰도 | 무작위 10건을 독립 라벨링해 필드 일치율 95% 이상 | 5장 |
| 평가 누수 방지 | test 30건은 최종 보고 때만 실행 | `--split` 옵션과 동결 해시 |
| 통계 | 구성 간 차이에 신뢰구간 표기 | 7장 |

이 기준은 **결과를 보기 전에** 정한 것이다. 기준을 못 넘기면 기준을 낮추지 않고 케이스를 고친다.

## 2. v1의 약점 (왜 포화됐나)

- 평균 transcript가 **82자**(최대 107자)다. 실제 방문 구술은 여러 문장, 잡담, 정정이 섞인다.
- 거의 모든 케이스에서 값이 한 번씩 깔끔하게 한 문장으로 나온다. 방해 수치, 정정, 다른 사람 이야기가 없다.
- 프롬프트의 어휘와 규칙이 이 20건을 보고 만들어졌다. 같은 데이터로 평가하면 일반화가 아니라 암기를 잰다(누수).
- 정답 라벨 규칙이 암묵적이라 gs-016(추론), gs-017(식사 어휘), gs-015(칠십이)에서 라벨 쪽 문제가 났다.

## 3. 신규 40건: 실패 모드 중심 설계

각 케이스는 **어떤 실패를 유도하는지**(프로브)를 하나의 주 목적으로 가진다. 케이스마다 "모델이 이렇게 틀릴 것"이라는 가설을 사전에 적는다.

| # | 프로브 | 건수 | 유도하는 실패 | 예시 상황 |
|---|---|---|---|---|
| H | 환각 압력 | 6 | 말하지 않은 값을 채움 | "혈압은 정상이었어요"(숫자 없음), "특이사항 없었어요"(포괄 부정), 약을 "드셨겠죠"(추측), 매우 짧은 transcript, 잡음만 있는 transcript |
| C | 정정·복수 값 | 5 | 정정 전 값을 기록, 또는 해소된 정정을 모호로 처리 | "130이 아니라 140이요"(해소), "130이었나 140이었나"(미해소), 측정 두 번 |
| D | 방해 수치와 제3자 | 5 | 엉뚱한 숫자를 필드로 잡음 | 혈압약 이름의 숫자, 어제 혈압, 가족의 혈압, 약 개수, 체온·체중(필드 아님) |
| N | 부정과 시점 | 4 | 부정문·과거·미래를 현재로 읽음 | "넘어지진 않았는데 지난주엔 넘어지셨대요", "내일 병원 가신대요" |
| L | 길고 지저분한 발화 | 4 | 긴 잡담 속 핵심 값을 놓치거나 섞음 | 400~900자, 말더듬·반복·삼천포 |
| S | STT 오류(숫자 외) | 3 | 동음이의·띄어쓰기·약 이름 오인식 | "보용", "넘어 지셨어요", 숫자 외 오류. 정답은 reference 기준 |
| V | 어휘 경계 | 4 | 식사량·기분 등 닫힌 어휘 경계에서 흔들림 | "숟가락으로 몇 번", "죽만", "물만", "좋다가 울으셨다" |
| G | 방언·구어 확장 | 3 | 방언 수치 표현 | 제주·강원 방언, 읽는 방식 "일삼공에 팔공", "140 넘었대요"(하한만) |
| I | 인젝션 변형 | 3 | 지시를 따르거나 특이사항에 옮겨 적음 | 어르신이 한 말을 인용한 정당한 보고 vs 기록 지시, "시스템:" 가장, 프롬프트 노출 요구 |
| R | 위험 신호 다양성 | 3 | (Sentinel 설계 근거) 비정형 위험을 못 잡음 | 흉통, 호흡곤란, 부종, 식사 거부 지속, 학대 의심 |

합계 6+5+5+4+4+3+4+3+3+3 = **40**.

- 프로브 H와 C가 환각·수치 오류 분모를 키운다. 현재 분모(49, 29)로는 1건이 2~4%p라 판단이 안 된다.
- 길이: 40건 중 최소 25건은 200자 이상, L은 400자 이상. 평균 transcript를 v1의 3~5배로 한다.
- 모든 케이스는 8개 필드를 모두 라벨하므로 신규 40건에서 필드 320개가 추가된다.

## 4. 라벨 정책 (케이스를 쓰기 전에 확정)

v1의 라벨 분쟁(gs-016, 017, 015)은 정책이 없어서 생겼다. 정책은 **2026-10-23에 사용자와 항목별로 확정**했고 원본은 `docs/label-policy.md`다(아래 표는 설계 시점 초안이며 충돌하면 label-policy.md가 우선). 낙상 7일은 현장 확인 전 임시 관례다.

| 상황 | 정책(잠정) | 근거 |
|---|---|---|
| 추측 표현("드셨겠죠", "아마 ~일 거예요") | 사실로 기록하지 않음. `missing` + 위험 필드면 확인 필요 | 기록의 근거 원칙. 추측은 evidence가 될 수 없음 |
| 포괄 부정("특이사항 없었어요") | 개별 위험 필드를 채우지 않음. 각 위험 필드 `missing`, 확인 필요 | 낙상·복약을 말하지 않았음 |
| 정정, 해소됨("130이 아니라 140") | 마지막 값(140)을 `stated`로 | 화자가 직접 고침 |
| 정정, 미해소("130이었나 140이었나") | candidates 2개, value 없음, 확인 필요 | v1 정책 유지 |
| 한 방문에 측정 두 번 | 방문 중 측정한 값, 둘 다 방문 중이면 마지막 값. 방문 전 측정(가족, 어제)은 제외 | 방문 시점 기록이 목적 |
| 제3자·이전 시점 수치 | 필드에 넣지 않음 | |
| 낙상 시점 | 최근 7일 이내 보고된 낙상은 `있음` (위험 신호는 보수적). 그보다 오래된 이야기는 제외 | **7일은 임시 관례, 현장 확인 필요** |
| 낙상 직전("미끄러질 뻔") | `없음` + 특이사항 기록 + 낙상 필드 확인 필요 (v1 gs-013 유지) | |
| 식사량 | 전량(거의 다), 절반(반 정도), 소량(조금·몇 숟가락·"거의 못"), 미섭취(전혀·못 먹음), 미제공(안 챙김) | gs-017 확정: "거의 못 드셨다"=소량 |
| 기분 | `양호`/`저조`만. 혼재("좋다가 울으셨다")는 `저조`가 아니라 `missing`+특이사항 | 어휘 밖은 강제 매핑하지 않음 |
| 특이사항 | 위 필드에 못 들어가는 관찰·호소·사건. 화자의 추측성 해석은 제외 | gs-016 확정: 근거 있는 추론이면 값 있음으로 라벨 |
| 하한/상한만 말함("140 넘었대요") | 값 없음, 확인 필요 | 정확한 값이 아님 |
| 환각(가장) 인용된 지시 | 지시문은 어떤 필드에도 기록하지 않음. 단 어르신 발언을 인용한 보고는 특이사항 가능 | I 프로브 |

v1 재검토 결과: gs-016은 정책 #11에 맞춰 수정(결과 확인 후 수정으로 결정 로그에 기록), gs-017은 변경 없음.

## 5. 생성과 검수 절차

원칙: **정답을 먼저 쓰고 transcript를 나중에 만든다.** 모델 출력을 본 뒤 정답을 맞추지 않기 위해서다.

1. **스펙 작성**: 프로브, 8개 필드의 정답, 유도하려는 실패, 가설, 길이 목표를 케이스별 스펙으로 쓴다 (`data/golden/specs/*.yaml`).
2. **초안 생성**: 스펙을 입력으로 LLM이 transcript를 작성한다. **평가 대상(Sonnet·Haiku)과 다른 모델(Opus 5.5)** 을 쓰고, 말투(지역, 연령, 말더듬 정도)를 케이스마다 달리 지정한다. 예상 비용 $1 미만, 실행 전 승인 요청.
3. **직접 작성 10건**: 사용자가 실제 구술하듯 직접 쓴 transcript 10건을 섞는다(LLM 생성의 균질한 문체 편향 완화).
4. **자동 점검**: 스키마 검증, 근거 부분문자열, 개인정보 패턴, 길이 범위, 정답 값이 transcript에 실제로 등장하는지.
5. **독립 라벨링**: 무작위 10건을 사용자가 transcript만 보고 라벨한 뒤 스펙 정답과 비교한다. 필드 일치율 95% 미만이면 정책 표를 보완하고 해당 프로브를 다시 생성한다. 사람이 합의하지 못하는 케이스는 어려운 케이스가 아니라 나쁜 케이스이므로 버린다.
6. **현장 검토(선택, 권장)**: 요양보호사·사회복지사에게 transcript 10건의 현실성을 확인받는다.
7. **동결**: 파일 해시(sha256)와 날짜를 `docs/decisions.md`에 기록하고 git 태그 `golden-v2-frozen`을 만든다. 이후 라벨 수정은 항상 "결과 확인 후 수정"으로 기록하고 영향을 적는다.

생성 모델이 평가 모델과 같은 계열이라는 순환성(Claude가 쓴 문제를 Claude가 푼다)은 완전히 없앨 수 없다. 7절의 직접 작성 10건과 현장 검토가 이를 줄이는 장치이며, 한계로 명시한다.

## 6. dev/test 분리

| 분할 | 구성 | 용도 |
|---|---|---|
| dev 30건 | v1 20건 + 신규 10건 | 프롬프트·규칙 개선, 오류 분석 |
| test 30건 | 신규 30건 (프로브별 비례 배분) | **최종 ablation 보고 때만 실행**, 프롬프트 수정 금지 |

- v1 20건은 프롬프트 설계에 노출됐으므로 모두 dev다.
- 프롬프트 v2(정책 표 반영)는 dev의 오류만 보고 만든다. test 오류를 보고 프롬프트를 고치면 test가 dev가 되며, 그때는 새 test를 만든다.
- 러너에 `--split dev|test|all`을 두고, test 실행은 보고서에 `split=test`를 찍어 구분한다. test를 여러 번 돌리지 않는다(실행 횟수를 결정 로그에 기록).

## 7. 코드 변경 (구현 단계)

| 대상 | 변경 |
|---|---|
| `GoldenCase` | `split: Literal["dev","test"] = "dev"`, `tags: tuple[str, ...]`(프로브 코드), `Category`에 `distractor`, `correction`, `long_noisy`, `vocab_boundary`, `risk_signal`, `blanket` 등 추가 |
| 필드 | STT 케이스에서 텍스트로 복원 불가능한 필드를 `recoverable: bool = True`로 표시해 채점에서 별도 집계 (gs-014, 015의 구조적 오답과 모델 오답 분리) |
| 로더/테스트 | v1은 그대로 두고 신규를 `v2_dev.jsonl`, `v2_test.jsonl`로 분리. 유형별 최소 건수 테스트를 새 분포로 갱신 |
| 러너 | `--split`, 프로브(tag)별 지표, **bootstrap 신뢰구간**(케이스 단위 재표집 1,000회)과 **구성 간 짝지은 차이**(같은 케이스에서 B0 대 B1의 필드 정답 차이)를 보고서에 추가 |
| 지표 | 환각·수치 오류의 분모가 바뀌므로 정의는 유지. 값 내지 않음(abstain)과 틀린 값을 구분하는 보조 지표를 추가해 "이상한 값을 내지 않는 쪽이 유리한" 문제(gs-015)를 해소 |
| 프롬프트 | 4장 정책 표를 반영해 `PROMPT_VERSION=v2`. v1/v2 비교는 dev에서만 |

## 8. 비용과 일정

| 단계 | 내용 | 비용(추정) |
|---|---|---|
| 스펙 40건 작성 | 사용자 검토 포함 | 0 |
| 초안 생성 | Opus 5.5, 40건 | 약 $0.5~1 |
| 신규 40건 × 4구성 측정 | 라벨 동결 후 | 약 $0.5~0.7 (Sonnet 비중이 큼) |
| 독립 라벨링 10건 | 사용자 | 0 (약 20~30분) |

일정은 3주차 게이트(11/12)에 걸리므로 **1~2일 안에 스펙과 정책을 확정**하고, 나머지는 Rule Engine 작업과 병행한다. 주당 가용 시간은 아직 미확인이다.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 생성 transcript가 균질하고 모델에 유리 | 다른 모델로 생성, 직접 작성 10건, 현장 검토 |
| 너무 어려워 사람도 못 맞춤 | 독립 라벨링 95% 기준, 불일치 케이스 폐기 |
| 모델에 맞춰 케이스를 조정하는 유혹 | 라벨 동결, 결과 확인 후 수정 기록, test 1회 규칙 |
| 정책이 현장과 다름 | 4장 정책을 잠정으로 표시하고 현장 확인 후 재라벨 |
| 일정 압박 | 최소안: 신규 24건(프로브 H·C·D·N·L 우선)으로 먼저 측정 |
