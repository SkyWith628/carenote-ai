# test 최종 보고 계획 (사전 등록, 실행 전, API 호출 없음)

목적: 동결된 test 30건(`golden-v2-frozen`, 매니페스트 v2.0)에서 ablation 표를 **한 번** 낸다. 이 문서는 test를 보기 **전에** 구성·지표·판정 규칙·승인액을 고정하는 사전 등록이다. 실행 후에는 이 문서의 규칙을 바꾸지 않고, 바꾸면 변경 사실과 이유를 결정 로그에 남긴다. test는 지금까지 어떤 모델로도 실행한 적이 없다(test 실행 0회).

## 0. 이전 문서의 정정
`docs/extractor-prompt-v4-design.md`와 결정 로그에 "H6는 헤드라인에서 제외 예정"이라고 쓴 부분은 **틀렸다**. 잠정 동결 규칙이 제외하는 것은 R3(gs-060)와 G1(gs-052) 두 건뿐이다. H6(gs-026)는 교체되어 복약을 언급하지 않는 케이스라 정책 #14(옛 H6의 복약 전언에서 나온 정책)에 의존하지 않으므로 **포함**한다. 정책 #14를 직접 시험하는 test 케이스는 없다.

## 1. 구성 (사전 고정)
| 계층 | 구성 | 목적 | 필수 |
|---|---|---|---|
| 1 | **프롬프트 v4(현재 기본)** × {Sonnet 5.5, Haiku 5.5} × {B0, B1} = 4구성 | 주 ablation 표: 모델 대 모델, 단일 LLM(B0) 대 근거 강제(B1) | 필수 |
| 2 | **프롬프트 v1(기준선)** × 같은 4구성 | 프롬프트 효과(v1 → v4)를 **독립 데이터**에서 확인. dev의 개선은 순환적이라 test만이 일반화 증거 | 권장 |
| 3 | Flagger KR-1 규칙의 효과 | 같은 모델 출력에 규칙 적용 전·후를 오프라인 재채점 | 추가 API 없음 |

- 모델 id·effort: `claude-sonnet-5-5`, `claude-haiku-5-5`, effort `medium`(기본). 프롬프트 sha256 앞 16자: v1 B0 `3678dc45a8c637dd`, B1 `0d99a5274fd582ee`, v4 B0 `a21f39ed9aaba29f`, B1 `353d6dae40973f03`. 실행 직전 다시 확인한다.
- 구성당 **정확히 1회** 실행한다. 같은 구성을 설정을 바꿔 다시 돌리지 않는다. API 실패로 끊기면 같은 명령을 다시 실행해 이어서 진행하는 것(캐시)은 재실행이 아니다.
- 실행 시작 후 프롬프트·모델·규칙·정답을 바꾸지 않는다.

## 2. 헤드라인 지표 (R3·G1 제외, 28건)
- **대상**: test 30건에서 `review_required`인 gs-052(G1), gs-060(R3)를 뺀 **28건**. 30건 전체 값은 병기한다(숨기지 않는다).
- **주 지표**: 필드 F1, **복원가능 필드만**(gs-046 S2 복약처럼 STT가 정보를 지워 글만으로 복원 불가능한 필드 제외). 이유: 텍스트만 보는 모든 구성이 구조적으로 틀리는 필드를 모델 성능에 섞지 않는다. 복원 불가 포함 F1, gray 제외 F1도 병기.
- **안전 지표**: 조용한 오답률(위험 필드, 값 + flag ok + 오답), 과다 확인률, 위험 recall, 확인 recall, 환각, 수치 오류, 근거 없는 값(B1은 구조상 0), 기권·오답. 위험 recall 등은 분모가 작아(test 위험 flag 정답 5건 안팎) **횟수로 보고하고 비율의 유의성은 주장하지 않는다.**
- **분해**: 프로브별(H C D N L S V G I R), 유형별. 프로브당 케이스가 2~5건이라 프로브별 수치는 서술용이다.
- **불확실성**: 케이스 단위 부트스트랩 95% 구간(28건), 구성 간 **짝지은** 차이.

## 3. 사전 등록 비교와 판정 규칙
| 비교 | 짝 | 주장 조건 |
|---|---|---|
| B1 − B0 | 같은 모델·프롬프트 | 아래 조건 |
| Sonnet − Haiku | 같은 변형·프롬프트 | 아래 조건 |
| v4 − v1 | 같은 모델·변형 | 아래 조건 |
- **조건(둘 다)**: ① 28건 짝지은 부트스트랩 95% 구간이 0을 포함하지 않는다, ② |ΔF1|이 실행 간 변동의 2배보다 크다. 변동은 dev Haiku 반복 실행에서 측정한 σ_run ≈ 0.5%p(합성 σ ≈ 0.7%p, 기준 약 1.4%p)를 쓴다. **Sonnet의 실행 간 변동은 측정하지 않았으므로** Sonnet이 낀 비교는 ①만 만족해도 "방향만" 쓰고 단정하지 않는다.
- 조건을 못 채우면 "구분 불가"로 쓴다. 한 번 실행이라 반복 평균이 없다.
- 점추정이 어느 쪽이든 결과를 그대로 보고한다. 결과가 나쁘다고 프롬프트·정답·규칙을 test에 맞춰 고치지 않는다.

## 4. 구현이 필요한 것 (실행 전, API 없이 테스트)
| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 러너에 **헤드라인 집계**: `review_required` 케이스를 뺀 지표와 복원가능 필드만의 지표, 부트스트랩 구간을 보고서(JSON·표)에 `headline`으로 추가. 30건 전체 값도 그대로 유지 | oracle 만점, null 하한, 제외 케이스가 정확히 gs-052·060, 기존 보고서 필드 불변 |
| 2 | `evaluation.compare`와 `variance`에 케이스 제외 옵션(`--exclude-review-required`) | 제외 후 짝지은 차이가 per-case 계산과 일치 |
| 3 | 최종 표 도구 `evaluation.final_table`: 8개 보고서를 읽어 구성 × 지표 표, 사전 등록 세 비교와 판정 라벨(차이 있음/구분 불가/방향만), KR-1 규칙 전후(재채점) 출력 | 합성 보고서로 단위 테스트, 사전 규칙 라벨 검증 |
| 4 | `--final-report` 실행 기록 보조: 실행 시작 시 결정 로그용 한 줄(구성, 시각, 프롬프트 해시, 커밋) 출력 | 출력 형식 테스트 |
| 5 | 사전 등록 커밋과 태그 `golden-v2-final-plan` | 게이트 통과 후 |

## 5. 실행 순서
1. **사전 점검**: `freeze --check` 일치, 작업 트리 깨끗, 게이트 3종, 프롬프트 해시, **공식 가격 문서로 단가 재확인**(현재 코드의 단가 기준일은 2026-10-06이라 3주 지났다. 달라졌으면 `pricing.py`를 먼저 고친다).
2. **(권장) Sonnet v4를 dev에서 먼저 한 번**: Sonnet은 v4를 한 번도 측정하지 않았다(`docs/ablation.md`). test에서 처음 만나는 일을 피하려고 dev 30건 Sonnet B0·B1을 먼저 돌려 프롬프트 호환 문제(예: 구조화 출력 실패)가 없는지 본다. 이 결과로 v4를 고치지 않는다(고장 확인용). 추정 약 $0.66.
3. 구현 완료와 사전 등록 커밋·태그.
4. 8구성 **dry-run**으로 test 호출 수(구성당 30건, 캐시 적중 0건)와 추정 확인(아래 표).
5. **test 실행** 순서(싼 것부터, 한 번에 하나씩, 실패하면 중단): Haiku v4 B0 → Haiku v4 B1 → Sonnet v4 B0 → Sonnet v4 B1 → (권장) Haiku v1 B0 → Haiku v1 B1 → Sonnet v1 B0 → Sonnet v1 B1. 보고서는 `docs/reports/test-final-{prompt}-{model}-{variant}.json`, 모두 `--split test --final-report --out`.
6. 최종 표 생성(`final_table`), 헤드라인과 전체 병기, KR-1 규칙 전후 재채점.
7. 결정 로그와 `docs/ablation.md`에 결과 기록, `freeze --write --revise "test 최종 보고 실행" --test-runs N`(N = 실행한 구성 수)으로 매니페스트에 test 실행 횟수 기록(v2.1). **실행 후 라벨 수정은 항상 "test 점수를 본 뒤의 수정"으로 표시한다.**
8. 이후: R3·G1 전문가 회신이 와서 정답이 바뀌면 개정(v2.2)하고 해당 두 케이스만 다시 채점·실행(8구성 × 2건, 약 $0.06)하며 헤드라인에 반영 여부를 표시.

## 7. 알려진 한계와 해석 주의
- **표본**: 헤드라인 28건이라 F1 구간이 ±3%p 안팎이다. 구성 간 1~2%p 차이는 구분되지 않을 가능성이 높다(dev에서 σ_run 0.5%p, 한 번 실행).
- **라벨 하한**: 사람과 정답의 불일치 하한이 약 7%(F2 미충족). 모델 오류로 보이는 것의 일부는 정책 해석 차이일 수 있다.
- **같은 계열**: 생성기(Claude Opus)와 평가 대상이 같은 Claude 계열이다. 직접 작성 7건(test)과 나머지 23건의 격차를 별도로 보고한다.
- **dev 오염 비대칭**: 프롬프트(v2~v4)와 Flagger 규칙은 dev 오류를 보고 만들었다. test가 처음으로 독립이다. dev 대비 test 점수가 낮아도 정상이다(표본 안 대 표본 밖).
- **임시 관례**: 낙상 7일 기준과 특이사항 risk 기준은 현장 확인 전이다. N1·N2(낙상 시점 케이스)는 이 관례에 따른 점수로 따로 표시한다.
- **R3·G1**: 전문가 검토 미실시. 헤드라인에서 빠지지만 30건 전체 값에는 포함해 병기한다.
- **KR-1**: Flagger 규칙은 표본 안(dev) 결과다. test에서 처음 일반화된다. 규칙 전후 비교가 test의 번복 케이스(C3 등)에서 오경보를 만드는지 확인한다.
- Sonnet v4는 dev에서도 측정하지 않았다(2번 사전 점검 권장).

## 8. 이 계획이 결정하지 못하는 것 (사용자 결정)
1. **계층 2(v1 기준선)를 포함할지**: 추가 약 $0.53(최대 노출 $2.79)으로 프롬프트 효과의 독립 확인을 얻는다. 권장.
2. **Sonnet v4 dev 사전 점검**을 먼저 할지: 약 $0.66. 권장(test에서 처음 만나는 일을 피함).
3. 반복 실행(Haiku를 test에서 3회 등)으로 실행 간 변동을 줄이는 안은 **"test는 1회" 규칙과 충돌**하므로 이 계획에 넣지 않았다. 원하면 규칙 변경으로 기록한 뒤 별도 승인이 필요하다.
