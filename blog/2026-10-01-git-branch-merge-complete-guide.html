강의 자료 branch_to_merge.sh는 파일 몇 개를 만들고, 브랜치를 여러 갈래로 나눈 뒤 다시 합치는 셸 스크립트입니다. 명령어 수는 많지 않지만, 같은 git merge가 어떤 때는 포인터만 옮기고 어떤 때는 새 커밋을 만드는 이유를 관찰하기 좋습니다.

이 글에서는 원본 66줄을 관련 설명 옆에 모두 수록하고, 브랜치와 HEAD, 스테이징, 병합 옵션, 충돌 해결, 복구, 원격 협업, rebase까지 연결합니다. 원본 코드 분석에서 얻은 예상과 실제 실행 결과를 구분합니다. 원본 스크립트와 아래 실습 예제는 이 글을 작성하면서 실행하지 않았습니다.

2. 브랜치·HEAD·커밋의 관계

그래프의 선을 이해하려면 파일보다 커밋의 연결을 먼저 봐야 합니다. Commit(커밋): 프로젝트 내용의 스냅샷과 작성 정보, 부모 커밋 참조를 기록한 객체입니다. Branch(브랜치): 특정 커밋을 가리키며 이동하는 이름입니다. 책갈피를 다른 페이지로 옮기듯 브랜치의 위치도 바뀝니다.

HEAD(현재 위치 참조): 보통 현재 작업 브랜치를 가리키는 참조입니다. 브랜치에 연결된 상태에서 커밋하면 해당 브랜치가 새 커밋을 가리킵니다. 브랜치를 거치지 않고 커밋을 직접 가리키는 detached HEAD(분리된 HEAD) 상태도 있으므로 HEAD가 언제나 브랜치 이름인 것은 아닙니다. Pro Git: 브랜치의 원리

공식 문서의 짧은 예제 — Pro Git: Branches in a Nutshell

git branch testing

공식 예제는 현재 커밋에 testing이라는 이름을 붙입니다. 원본은 같은 동작을 반복문으로 확장합니다. 브랜치 이름이 develop1-feature1이라고 해서 Git이 부모·자식 규칙을 자동으로 부여하지는 않습니다. 출발 커밋과 이후 이력이 실제 관계를 결정합니다.

위 첫 줄은 개념 표기이며, 아래 두 줄은 관찰 명령

HEAD → develop1 → 커밋 D

# 현재 위치와 부모 정보 관찰

 git show --no-patch --format=raw HEAD

일반 커밋은 부모가 하나, 최초 커밋은 부모가 없고, 병합 커밋은 부모가 여러 개입니다. 파일 최종 내용이 같더라도 부모가 다르면 커밋의 의미와 이력은 달라집니다.

🔗 어디에 쓰나 — 브랜치를 전환한 뒤 엉뚱한 곳에 커밋하는 실수를 줄이려면 작업 전 현재 브랜치와 HEAD를 확인합니다. 팀 규모가 커져도 이 기본 모델은 같습니다.

→ 다음은 커밋에 들어갈 내용을 고르는 스테이징입니다.

3. 기본 파일 생성과 스테이징

기록할 위치를 알았다면 내용을 골라야 합니다. Working tree(작업 트리): 실제로 편집하는 파일 공간, Index / staging area(인덱스·스테이징 영역): 다음 커밋에 담을 내용을 준비하는 공간입니다. 장바구니에 담은 물건만 결제하듯, 기본적인 commit은 스테이징된 내용을 기록합니다.

강의 원본 4–9행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

git init
for i in $(seq 1 3)
do
  echo "Master -> $(date)" > file$i.yaml ; sleep 1 ; git add . ; git commit -m "1st commit without merge"
done

반복마다 file1.yaml, file2.yaml, file3.yaml을 하나씩 생성하고 커밋합니다. 기본 커밋은 3개입니다. 세 메시지가 모두 1st commit without merge여도 실제 파일 변경이 다르므로 별개의 커밋입니다. 파일 확장자는 이 실습의 Git 동작에 영향을 주지 않습니다.

공식 문서에 제시된 비교 형식 — git diff

git diff --cached

공식 문서에서 git diff는 작업 트리와 인덱스 차이, git diff --cached는 인덱스와 현재 커밋의 차이를 보여줍니다. 원본은 곧바로 add와 commit을 실행하므로 이 중간 상태를 관찰하기 어렵습니다. 공식 문서: git diff

직접 구성한 학습 예제

# file1.yaml이 이미 추적되는 실습 저장소에서
printf '\nfirst change\n' >> file1.yaml
git diff
git add file1.yaml
git diff --cached
printf 'second change\n' >> file1.yaml
git diff
# 예상: 마지막 diff에는 add 이후의 second change가 보임
# 첫 수정만 스테이징되어 있으며 두 번째 수정은 아직 작업 트리에만 있음

What — 두 비교 명령으로 다음 커밋 내용과 아직 담지 않은 내용을 구분합니다. Why — add 이후의 편집은 자동으로 스테이징되지 않기 때문입니다. How — 실무에서는 필요한 파일만 add하고 cached diff를 검토한 뒤 커밋합니다. 원본의 git add .는 현재 디렉터리 아래 다른 변경까지 포함할 수 있습니다. 공식 문서: git add

🔗 어디에 쓰나 — 하나의 커밋에 한 가지 목적을 담으면 리뷰, 오류 원인 추적, 나중에 되돌리기가 쉬워집니다.

4. develop과 feature의 출발점

강의 원본 10–16행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

sleep 2
git switch main || git switch master 
for i in $(seq 1 3)
do
  git branch develop$i
done

git switch main || git switch master는 main 전환을 먼저 시도하고 실패하면 master를 시도합니다. 전환에 성공한 위치에서 브랜치 3개를 생성합니다. git branch는 생성만 하므로 세 develop은 기본 커밋 3개가 쌓인 동일 지점에서 출발합니다. 공식 문서: git branch

강의 원본 17–31행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

sleep 2
for i in $(seq 1 3)
do
git switch develop$i
echo "develop1 -> $(date)" >> file$i.yaml ; sleep 1 ;  git add . ; git commit -m "develop$i >> fileA commit1"
echo "develop1 -> $(date)" >> file$i.yaml ; sleep 1 ;  git add . ; git commit -m "develop$i >> fileA commit2"
  for j in $(seq 1 2)
  do
  git branch "develop$i-feature$j" "develop$i"
  git switch "develop$i-feature$j"
  echo "develop$i-feature$j -> $(date)" >> file$i$j.yaml ; sleep 1 ;  git add . ; git commit -m "develop$i-feature$j >> file$i$j commit1"
  echo "develop$i-feature$j -> $(date)" >> file$i$j.yaml ; sleep 1 ;  git add . ; git commit -m "develop$i-feature$j >> file$i$j commit2"
  done
done

각 develop에서는 대응하는 기본 파일에 두 줄을 추가하며 두 번 커밋합니다. 이후 feature 두 개를 각각 만들고 전용 파일에 두 번 커밋합니다.

develop수정 파일feature1 / feature2의 파일
develop1file1.yamlfile11.yaml / file12.yaml
develop2file2.yamlfile21.yaml / file22.yaml
develop3file3.yamlfile31.yaml / file32.yaml

공식 git branch <branchname> [<start-point>] 형식과 대조하면 원본의 두 번째 인수 "develop$i"가 중요합니다. feature1에서 작업을 마치고 그 브랜치에 머물러 있어도, feature2의 출발점은 명시한 develop입니다. 두 feature는 형제 관계입니다. 공식 testing 예제는 현재 위치를 사용하고, 이 실습은 출발점을 명시한다는 차이가 있습니다.

⚠️ 원본의 표기 오류: develop2·develop3에서도 파일에 기록하는 문자열이 develop1입니다. 커밋 메시지의 fileA도 실제 파일명과 다릅니다. 파일 선택과 브랜치 이동 자체는 변수 i를 사용하므로, 이 두 표기는 동작보다 이력 해석을 혼란스럽게 만듭니다.

직접 구성한 학습 예제

# 원본을 수정한다면 사용할 수 있는 표기 예시 — 이 글에서는 원본 수정 안 함
echo "develop$i -> $(date)" >> "file$i.yaml"
git add "file$i.yaml"
git commit -m "develop$i: update file$i.yaml"
🔗 어디에 쓰나 — 브랜치를 자동 생성하는 스크립트에서는 현재 위치에 의존하기보다 출발점을 명시하면 의도하지 않은 연쇄 분기를 줄일 수 있습니다.

5. feature를 develop으로 병합하기

Merge(병합): 다른 이력을 현재 브랜치에 통합하는 작업입니다. Fast-forward(빨리 감기 병합): 현재 커밋이 상대 이력의 조상일 때 브랜치 위치만 앞으로 옮기는 방식입니다. 중간 페이지를 건너 책갈피만 뒤로 옮기는 상황과 비슷합니다.

공식 Pro Git의 짧은 예제 — Basic Branching and Merging

git merge hotfix

공식 예제는 현재 브랜치에 hotfix를 합칩니다. 원본도 같은 방향이며, 먼저 develop으로 전환한 뒤 feature를 합칩니다. Pro Git: 기본 브랜치와 병합

강의 원본 32–41행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

sleep 2
for i in $(seq 3 -1 1)
do
  git switch "develop$i"
  for j in $(seq 2 -1 1)
  do
    git merge "develop$i-feature$j" --no-edit
  done
done

반복 순서는 develop3 → 2 → 1이고, 각 develop에서는 feature2 → feature1입니다. 아직 develop에 별도 커밋이 없으므로 feature2는 Fast-forward가 가능합니다. 이후에는 두 feature의 독립적인 커밋을 연결해야 하므로 feature1 병합에서 부모가 둘인 커밋이 만들어집니다.

원본의 순서에 따른 예상 그래프 · 기본 병합 설정 가정

# 병합 전: D는 develop의 끝
      A1──A2  feature1
     /
D───┤
     \
      B1──B2  feature2

# feature2를 먼저 병합: develop도 B2를 가리킴
# feature1까지 병합 후:
      A1──A2─────┐
     /           \
D───┤             M  develop
     \           /
      B1──B2─────┘

파일을 합치는 방향과 브랜치 이동을 혼동하기 쉽습니다. git merge feature는 feature로 이동하는 명령이 아닙니다. 변경을 받는 쪽은 현재 브랜치입니다. 이 원본은 각 feature가 다른 파일을 추가하므로 충돌 없이 이력 모양을 관찰하도록 구성되어 있습니다.

🔗 어디에 쓰나 — 독립적인 기능을 합칠 때도 어느 브랜치가 통합 대상인지 먼저 확인합니다. 자동 병합 성공 후에는 기능 조합이 올바른지 테스트합니다.

→ 다음은 상위 브랜치 통합과 이력 보존 방식의 선택입니다.

6. develop 통합과 병합 옵션 비교

강의 원본 42–48행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

sleep 2
git switch  master || git switch main
for i in $(seq 3 -1 1)
do
git merge  "develop$i" --no-edit
done

마지막 통합은 develop3 → develop2 → develop1 순서입니다. 기본 브랜치는 분기 이후 움직이지 않았으므로 첫 통합은 Fast-forward, 이후 두 통합은 병합 커밋 생성으로 예상합니다. develop마다 다른 기본 파일을 수정하므로 이 예제의 변경은 충돌하지 않습니다.

여기서 --no-edit는 기본 메시지를 그대로 사용하는 옵션입니다. 병합 커밋 생성 여부는 다음 옵션과 이력 관계에 달려 있습니다. 공식 문서: git merge

옵션동작실무 선택과 비용
--ff가능하면 Fast-forward, 아니면 병합 커밋일반적인 통합. Fast-forward에서는 별도 병합 경계가 남지 않음
--no-ff통합할 변경이 있으면 Fast-forward가 가능해도 병합 커밋기능 단위를 추적하기 좋지만 커밋 그래프가 복잡해짐
--ff-onlyFast-forward가 불가능하면 실패예상하지 못한 분기를 드러내고 임의 병합 방지
--squash합쳐진 결과를 준비하고 커밋은 따로 수행기능 단위로 간결하게 기록하지만 원래 이력의 병합 연결은 남기지 않음

Squash(커밋 압축): 여러 변경을 하나의 커밋으로 기록하도록 모으는 방식입니다. git merge --squash 뒤 commit을 실행하면 일반적인 한 부모 커밋이 생깁니다. feature 브랜치의 기존 커밋 자체가 사라지는 것은 아닙니다.

직접 구성한 학습 예제

# 서로 동일한 병합 전 상태에서 하나씩 비교할 명령
# 모두 연속으로 실행하는 예제가 아닙니다.
git merge --ff feature
git merge --no-ff feature
git merge --ff-only feature

# squash 방식만 선택한 경우
git merge --squash feature
git diff --cached
git commit -m "Integrate feature"

이미 병합한 상태에서 옵션만 바꿔 실행하면 보통 새 비교가 되지 않습니다. 같은 출발 상태의 별도 실습 저장소로 비교해야 합니다. --no-commit만으로는 Fast-forward 갱신을 멈출 수 없다는 점도 공식 문서에서 확인할 수 있습니다.

🔗 어디에 쓰나 — 기능 병합의 경계를 보존할지, 기능당 한 커밋으로 정리할지를 팀에서 합의합니다. 어느 옵션도 코드 품질 검증을 대신하지는 않습니다.

강의 원본 49–64행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

##for i in $(seq 3 -1 1)

##sleep 2

브랜치 삭제 부분은 전부 주석입니다. 따라서 원본을 실행해도 이름 10개가 남습니다. git branch -d는 브랜치 이름을 삭제하는 작업이며, 병합된 변경을 기본 브랜치에서 제거하는 작업이 아닙니다. 삭제 허용 여부는 upstream이 있으면 그쪽, 없으면 HEAD로의 병합 상태를 기준으로 검사합니다. 공식 문서: git branch

강의 원본 65–66행 · 원문 그대로 · 실행 결과는 아래에서 별도 설명

rm file*
git add . ; git commit -m "La Fin"

반면 마지막 두 줄은 주석이 아닙니다. rm file*은 현재 디렉터리의 file로 시작하는 이름을 대상으로 삭제를 시도하고, 그 상태를 La Fin이라는 커밋으로 기록합니다. 깨끗한 실습 환경이라면 생성한 파일 9개가 사라집니다. 이전 커밋에 기록된 파일 내용까지 지우는 것은 아닙니다.

⚠️ 실습과 무관한 file* 파일도 삭제 대상이 될 수 있습니다. 특히 추적하지 않은 파일의 삭제를 Git이 자동으로 복구해 주지는 않습니다. 원본은 별도의 빈 실습 폴더에서만 다루는 편이 적절합니다.
🔗 어디에 쓰나 — 브랜치 정리는 이름 관리이고, 파일 삭제 커밋은 프로젝트 내용 변경입니다. 둘을 구분해야 “브랜치를 지우면 기능도 사라지나?” 같은 혼동을 피할 수 있습니다.

확인한 점영향개선 방향
현재 폴더에서 git init기존 저장소를 재초기화해도 별도 격리 공간이 되지 않음빈 전용 디렉터리에서 시작
main/master 전환 순서가 앞뒤에서 다름두 이름이 모두 있으면 생성 기준과 최종 통합 대상이 달라질 수 있음실습에서는 기본 브랜치 하나로 통일

CRLF / LF(줄바꿈 형식): 각각 두 문자와 한 문자로 줄 끝을 표현하는 방식입니다. 원본에서 CRLF를 확인했으므로 실행한다면 사본을 정규화해야 합니다. 저장소 초기화가 기존 파일을 격리하지 않는다는 점은 공식 문서: git init에 설명되어 있습니다.

9. 충돌을 직접 만들고 해결하기

정상 병합을 이해했다면 자동 통합이 멈추는 상황을 만들어 볼 차례입니다. Conflict(충돌): Git이 변경을 자동으로 결합하지 못해 사람이 최종 내용을 결정해야 하는 상태입니다. 두 사람이 같은 문장을 다르게 고친 상황을 생각하면 됩니다. 같은 파일을 수정했다고 항상 충돌하는 것은 아니며, 같은 줄을 서로 다르게 바꾸면 재현하기 쉽습니다. Pro Git: 기본 병합 충돌

공식 Pro Git 충돌 예제에서 사용하는 확인 명령

git status

강의 원본에는 충돌을 만드는 코드가 없습니다. 아래는 독립적인 새 폴더에서 실행하도록 직접 구성한 확장 예제입니다. Git 작성자 설정이 되어 있어야 commit이 성공합니다.

직접 구성한 학습 예제

# 기존 프로젝트 밖에서, 같은 이름의 폴더가 없는 상태로 실행
mkdir git-conflict-lab
cd git-conflict-lab
git init -b main
printf 'color=blue\n' > config.txt
git add config.txt
git commit -m "Initial color"
git switch -c feature
printf 'color=red\n' > config.txt
git add config.txt
git commit -m "Feature color"
git switch main
printf 'color=green\n' > config.txt
git add config.txt
git commit -m "Main color"
git merge feature
# 예상: config.txt의 같은 줄이 달라 병합 중단
git status
git diff

직접 구성한 학습 예제

# 위 충돌이 발생한 뒤 최종 의도를 결정해 파일 수정
printf 'color=purple\n' > config.txt
git add config.txt
git merge --continue
# 편집기가 열리면 병합 이유를 작성하고 저장·종료

# 해결 대신 취소하기로 했다면, 해결 완료 전에 이것을 선택
# git merge --abort

What — 두 변경의 의도를 반영한 최종 내용을 저장합니다. Why — 충돌 표시는 문법적 경계일 뿐 정답을 알려주지 않기 때문입니다. How — 실제 코드에서는 관련 테스트를 실행한 뒤 병합을 완료합니다. 미커밋 변경이 있는 상태로 시작하면 abort가 원래 상태를 완전히 되살리지 못할 수도 있습니다. 공식 문서: git merge

🔗 어디에 쓰나 — 자동 병합 성공은 의미적 정확성을 보장하지 않습니다. API 변경과 호출부 변경이 서로 다른 파일에 있어도 통합 후에는 실패할 수 있으므로 통합 테스트가 필요합니다.

→ 다음은 이미 반영한 변경을 되돌리는 방법입니다.

10. restore·reset·revert 구분하기

문제가 생겼을 때는 무엇을 되돌릴지 먼저 정합니다. Restore(복원): 파일이나 스테이징 내용을 선택한 상태로 되돌리는 명령, Reset(참조·상태 재설정): 형식과 옵션에 따라 브랜치 위치나 인덱스 등을 바꾸는 명령, Revert(역변경 기록): 기존 변경을 취소하는 새 커밋을 만드는 명령입니다.

공식 git restore 예제 발췌

git restore --staged hello.c

공식 예제와 같은 방식으로 git restore --staged file1.yaml을 실행하면 작업 파일 수정은 유지하고 스테이징을 되돌립니다. --staged 없이 파일을 restore하면 작업 파일의 수정 내용을 버릴 수 있으므로 옵션을 구분해야 합니다. 공식 문서: git restore

공식 git reset 예제의 핵심 명령 발췌

git reset --soft HEAD^

현재 브랜치에 있고 이전 커밋이 있는 상황에서 git reset --soft HEAD~1은 브랜치를 한 단계 뒤로 옮기되 인덱스와 작업 파일은 유지합니다. HEAD~1과 HEAD^는 여기서 첫 번째 부모를 가리킵니다. --mixed는 인덱스도 맞추며 작업 파일은 유지하고, --hard는 작업 파일까지 맞추므로 변경 손실 위험이 있습니다. 경로를 지정하는 reset은 브랜치를 옮기지 않는 다른 형식입니다. 공식 문서: git reset

공식 git revert 예제 발췌 — 현재에서 첫 부모를 세 번 따라간 커밋 하나의 변경을 취소

git revert HEAD~3

revert는 과거를 잘라내는 대신 취소 사실을 이력에 추가합니다. 공유한 커밋을 되돌릴 때 검토하기 좋은 방식입니다. 공식 예제의 HEAD~3은 최근 세 커밋 전체를 취소한다는 뜻이 아닙니다. 공식 문서: git revert

목적명령작업 내용
add 취소git restore --staged file1.yaml파일 수정 유지
로컬 마지막 커밋 재정리git reset --soft HEAD~1변경은 스테이징에 유지
기록된 변경 취소git revert <커밋-ID>취소 커밋 추가

직접 구성한 학습 예제

# 원본 실습이 정상 완료되고 마지막 커밋이 La Fin인 상태에서만
git log -1 --oneline
git status
# 작업 트리가 깨끗한 것을 확인한 뒤
git revert --no-edit HEAD
# 예상: 삭제된 실습 파일 9개가 새 커밋과 함께 복원됨

강의의 마지막 삭제를 복구하는 연습입니다. 이미 다른 커밋을 만들었다면 HEAD를 그대로 쓰지 말고 La Fin의 ID를 지정해야 합니다. 병합 커밋의 revert는 기준 부모를 고르는 별도 판단이 필요하므로 이 단일 부모 예제와 구분합니다.

🔗 어디에 쓰나 — 배포된 변경을 취소할 때는 revert가 협업 이력을 보존합니다. 아직 공유하지 않은 개인 커밋을 다시 나눌 때는 reset을 고려할 수 있습니다.

→ 다음은 브랜치에서 보이지 않게 된 커밋을 찾는 기록입니다.

11. reflog로 이전 커밋 찾기

Reflog(참조 변경 기록): 로컬에서 HEAD와 브랜치 참조가 이동한 이력을 남기는 기록입니다. 커밋 그래프가 연결된 작업 이력이라면 reflog는 로컬 위치 이동 기록에 가깝습니다. 공식 문서: git reflog

공식 문서는 git reflog show라는 사용 형식을 제공합니다. 아래 복구 시나리오는 공식 문서의 완성형 예제를 복제한 것이 아니라 직접 구성한 연습입니다. 강의 원본에는 reflog 사용이 없습니다.

직접 구성한 학습 예제

# 둘 이상의 커밋이 있는 별도 실습 브랜치, 깨끗한 작업 상태에서
git reset --soft HEAD~1
git reflog
# 출력에서 reset 직전 커밋 ID를 찾기
# 아래 COMMIT_ID를 확인한 실제 ID로 바꿉니다.
git branch recovery COMMIT_ID
git log --graph --all --oneline --decorate
# 예상: recovery가 reset 직전 커밋을 가리킴

이 연습의 reset --soft는 파일 수정과 인덱스를 그대로 둡니다. recovery를 만드는 것만으로 작업 트리를 다시 바꾸지는 않습니다. 복구 위치를 먼저 확보하고 이후 상태 정리를 결정하는 방식입니다. reflog에는 만료 정책이 있으며 커밋하지 않은 모든 편집 내용을 보관하지 않습니다. 영구 백업으로 간주하면 안 됩니다.

🔗 어디에 쓰나 — 잘못 reset한 직후에는 더 많은 변경보다 reflog 확인과 복구 브랜치 생성이 먼저입니다. “커밋이 현재 log에 안 보임”과 “객체가 영구적으로 삭제됨”을 구분합니다.

→ 다음은 로컬 이력을 다른 저장소와 주고받는 협업입니다.

12. 원격 브랜치와 fetch

Remote(원격 저장소): 다른 저장소에 연결한 이름과 주소입니다. Remote-tracking branch(원격 추적 브랜치): 마지막 통신에서 확인한 원격 브랜치 위치를 로컬에 기록한 참조입니다. 예를 들어 origin/main은 서버의 실시간 화면보다 마지막 동기화 시점의 메모에 가깝습니다.

공식 Pro Git: Remote Branches의 예제 명령

git fetch origin

공식 예제의 fetch는 원격 객체와 참조 정보를 가져옵니다. 로컬 main과 origin/main은 별개이며, fetch만으로 현재 브랜치에 자동 병합되지는 않습니다. 강의 원본에는 원격 연결이나 fetch가 없습니다. Pro Git: 원격 브랜치

직접 구성한 학습 예제

# origin 원격에 main이 있고 로컬 main도 존재하는 저장소에서
git fetch origin
git log --graph --all --oneline --decorate
git switch main
git merge --ff-only origin/main
# 예상: FF 가능하면 main 갱신, 양쪽이 갈라졌으면 실패

What — 변경 가져오기와 통합을 분리합니다. Why — 원격 상태를 먼저 관찰할 수 있기 때문입니다. How — 실패했다고 곧바로 강제 덮어쓰지 말고 로컬 커밋이 생긴 이유부터 확인합니다. pull은 가져오기 이후 설정·옵션에 따른 통합을 수행하므로 학습 초기에 이 두 단계를 나누면 이해하기 쉽습니다.

🔗 어디에 쓰나 — 협업 중 “서버에는 반영됐는데 내 origin/main에는 없다”면 마지막 fetch 시점을 확인합니다. 팀의 통합 규칙도 함께 맞춥니다.

→ 다음은 갈라진 이력을 정리하는 또 다른 방법입니다.

13. merge와 rebase의 선택

Rebase(기준 변경): 브랜치의 커밋을 다른 기준점 위에 다시 적용하는 작업입니다. 변경 내용을 최신 문서 위에 다시 작성하는 과정으로 생각하면 됩니다. 기존 부모 관계를 이어 붙이는 merge와 결과 그래프가 다릅니다.

공식 git rebase 설명의 예제 — topic 브랜치에 있는 상황

git rebase master

공식 예제는 topic의 커밋을 master 위에 다시 적용합니다. 아래 학습 예제에서는 이름을 main과 feature로 바꿨습니다. 강의 원본은 merge만 사용하므로 rebase는 추가 학습 범위입니다. 공식 문서: git rebase

직접 구성한 학습 예제

# main과 feature가 있는 별도 실습 저장소, 깨끗한 작업 상태에서
git switch feature
git rebase main
# 충돌이 발생하면 파일 수정 후
# git add <해결한 파일>
# git rebase --continue
# 취소하려면 git rebase --abort

직접 그린 개념 그래프 · A′, B′는 재작성된 커밋

# 재적용 전
      A──B  feature
     /
C───D──E  main

# 재적용 후
C───D──E──A′──B′  feature
       ↑
      main

부모가 바뀌어 새 커밋이 만들어지면 ID도 달라집니다. 항상 무조건 새 ID가 생긴다고 일반화할 수는 없지만, 이력 재작성을 전제로 협업 영향을 판단해야 합니다. 다른 사람이 기반으로 사용한 이력을 재작성하면 동료도 이력을 정리해야 할 수 있습니다.

기준mergerebase
이력기존 커밋 관계를 보존하며 통합기준점 위에 재적용
장점분기와 통합 과정을 추적하기 쉬움개인 작업 이력을 선형으로 정리하기 좋음
비용분기가 많으면 그래프가 복잡재작성된 이력을 공유할 때 조율 필요
충돌병합 단계에서 해결여러 커밋을 재적용하며 반복 해결할 수도 있음
🔗 어디에 쓰나 — 개인 feature를 최신 main 위에 정리할 때 rebase를 고려합니다. 공유 브랜치에서는 팀 정책과 다른 사람의 작업 기반을 먼저 확인합니다.

14. 실무·면접 포인트와 학습 순서

이 실습은 develop을 세 개 만드는 그래프 연습입니다. 브랜치 이름만 보고 특정 팀의 표준 운영 전략이라고 받아들일 필요는 없습니다. 실무에서는 기능 크기, 리뷰 주기, 배포 방식에 맞춰 정책을 정해야 합니다.

질문설명할 핵심
왜 브랜치를 쓰나요?작업 이력을 분리하고 검토 후 통합하기 위해 사용합니다.
왜 첫 merge는 커밋이 없나요?현재 커밋이 대상의 조상이면 위치 이동만으로 이력을 포함할 수 있기 때문입니다.
merge와 squash 중 무엇을 고르나요?분기·통합 관계 보존과 기능 단위의 간결한 이력 중 팀의 우선순위를 선택합니다.
충돌 해결 완료는 어떻게 판단하나요?표시 제거뿐 아니라 변경 의도를 검토하고 관련 테스트가 통과했는지 봅니다.
팀 규모가 10배가 되면요?작은 변경 단위, 짧은 브랜치 수명, 일관된 리뷰·통합 규칙, 자동 테스트를 강화하겠습니다.
장애가 나면요?공유 변경은 revert를 우선 검토하고, 로컬 참조 실수는 reflog로 복구 지점을 찾겠습니다.
보안은 어떻게 확인하나요?커밋 전에 스테이징된 diff를 검토해 토큰·비밀번호·개인정보가 포함되지 않도록 합니다.

실습을 다시 할 때는 다음 순서가 좋습니다. 각 단계에서 예상 그래프를 먼저 그린 뒤 실제 출력과 비교하면 명령 암기에서 벗어날 수 있습니다.

  1. add 전후와 add 이후 재수정의 diff를 비교합니다.
  2. 동일한 시작 상태에서 기본 merge, --no-ff, --ff-only, squash를 비교합니다.
  3. 같은 줄을 다르게 고쳐 충돌을 만들고 해결 또는 abort를 선택합니다.
  4. 원본의 La Fin 커밋을 revert하여 삭제 복구를 확인합니다.
  5. 별도 실습에서 soft reset 후 reflog로 복구 브랜치를 만듭니다.
  6. 원격이 있는 저장소에서 fetch 전후 origin/main을 비교합니다.
  7. 개인 feature에서 rebase 전후 커밋 ID와 그래프를 비교합니다.
📌 면접 답변 예시: “브랜치는 커밋을 가리키는 참조입니다. 현재 커밋이 병합 대상의 조상이면 Fast-forward로 이동할 수 있습니다. 두 브랜치에 독립적인 커밋이 있으면 일반적인 merge는 두 이력을 연결하는 커밋을 만들며, 충돌 여부와 별개로 통합 결과를 테스트해야 합니다.”

→ 다음은 필요할 때 다시 찾을 치트시트입니다.

15. 치트시트와 핵심 요약

목적명령조건·주의
그래프 확인git log --graph --all --oneline --decorate브랜치 이름과 커밋 연결 함께 확인
부모 확인git show --no-patch --format=raw HEAD일반·병합 커밋 비교
작업 파일 변경git diff인덱스와 비교
다음 커밋 검토git diff --cached현재 커밋과 인덱스 비교
출발점 지정git branch feature develop생성만 하며 전환은 별도
병합 경계 보존git merge --no-ff feature현재 브랜치로 통합
FF만 허용git merge --ff-only origin/main분기했으면 실패
충돌 해결 계속git merge --continue해결 파일 add 후
진행 중 병합 취소git merge --abort완료된 병합 취소 명령 아님
스테이징 취소git restore --staged file1.yaml작업 파일은 유지
로컬 커밋 풀기git reset --soft HEAD~1공유 이력 재작성 주의
취소 커밋 추가git revert <ID>병합 커밋은 별도 판단 필요
복구 위치 확인git reflog영구 백업 아님
커밋 확보git branch recovery <ID>실제 확인한 ID 사용
원격 변경 가져오기git fetch origin현재 브랜치에 자동 병합 안 함
기준 변경git rebase main개인 작업·팀 정책 확인
💡 핵심 7가지
1. 브랜치는 커밋을 가리키고 HEAD는 보통 현재 브랜치를 가리킵니다.
2. add 이후 수정은 다음 커밋에 자동 포함되지 않습니다.
3. Fast-forward 가능 여부는 파일 개수가 아니라 이력 관계로 결정됩니다.
4. --no-edit는 메시지 옵션이며 --no-ff와 다릅니다.
5. 충돌 표시를 없앴더라도 동작 검증은 필요합니다.
6. restore·reset·revert는 되돌리는 대상이 다릅니다.
7. fetch와 통합을 구분하고 공유 이력 재작성은 팀과 조율합니다.
